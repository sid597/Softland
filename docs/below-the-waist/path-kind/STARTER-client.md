## The builder (both lanes, this round)

`````
Fence: code only under `src/app/client/`; never `src/app/server/env.clj`. You work in your own git worktree on your own branch (`waist/path-<your model family>`), committing there with exact paths; `main` is not yours this round, another session builds the same thing from this same starter on its own branch, and the 3D chair commits to `main`. The work-package skill and its contract-and-gate process are not used for this work; where an older handoff points at them, this supersedes it.

What I am building is every 2D tool as data above a waist of code that exists once, so that humans and agents can create, edit and reuse tools as records. The exploration of the path kind is done. Four attacks were folded and the picture held at six pieces: the path type, the geometry, the packer, the filler, the executor and the compositor. I ruled three things: a varying width is the swept round nib, because it looks good on the drawing surface and nothing more; behaviour as data runs on the executor, records over a vocabulary of capabilities; and the compositor is one piece with two operations, paint and sample, owning clips, blends, layers, the screen and the surface a brush reads, painting and vector sharing it. Our aim is not to copy anyone. The best in the field is a datapoint and we go with the best experience for this field. From the start there is no concept of carrying forward an existing solution if that is not how it should be.

The prototype is done: the bench is satisfied from both models, and what remains is production. There is no contract to write first and no test suite to write before the code. Build the tests yourself as you build. The documentation lives where the code lives, in the hierarchy from the READMEs down to the docstrings down to the code, which carries what is implemented and how, and it changes in the same commit as the code. The question to hold is how the best team in the world for this would do it, nothing else. Functions follow the functional programming rule: transformations pure and composable with explicit inputs and outputs; mutable storage, asynchronous work and GPU effects with explicit owners and lifetimes. One thing to work out early: where the data layers and the data flow are, and where reactive programming belongs here, if anywhere. What to do and how to do it next is up to you.

Terrain. Everything is under `docs/below-the-waist/path-kind/`. The page `path-kind.html` (twin `path-kind.md`) holds the picture, the contract block (what a record declares, what the kind takes and returns, the compositor's two operations), the rulings on its ledger with the time, and the cascade table of where each piece was thought to land in cljc, which under my ruling on carrying forward is a datapoint. The bench `bench-9/waist-bench.html` is the working prototype of the waist in one WebGL2 file with its handover `bench-9/HANDOVER.md`: the record vocabulary, the definer's records as fixtures with their measured numbers, and `bench-9/node-route/`, which runs the pure declarations in Node as tests. The bench's meanings and behaviours are established through those constructions; its implementation shortcuts, such as the depth-limited reachability walk and the one-page content store, are not production requirements. The definer's `from-12-to-client.md` proposes the first client change: replace the path triangle route with the common path value and shared curve coverage, run the pen, draw and border records through it including the pressure stroke's union and accumulation, take the coverage implementation out of the text renderer while text keeps its layout and glyph packing, replace the old shaders, mesh preparation and zoom bands, and move the ink-on-plane consumer in `region3d/on_plane.cljc` too, since it uses the same tessellator; it names the callers and their proposed replacements. `HANDOFF-12.md` and the handoffs before it carry the round; `HANDOFF-8.md` section 5 holds the code facts of the tree with file and line, including how a frame flows today from the harness through the component and the tessellation to the renderer; `fact-base-12.md` and the earlier fact bases hold every measurement. The client's reactive laws and recipes are the `electric-docs` skill, Missionary only: Electric is not a dependency and the courier is owned. `docs/below-the-waist/two-chairs.md` is the two roles' workflow. Memory holds the proven roads for driving the app and for a WebGL2 bench headless.
`````
