The Parked Render Engine

The kept-code map drew the parked render engine as eight boxes. This page opens those eight one notch — each into its pieces — and answers two questions in plain words: how is an engine like this built at all, and how is ours built, and why that way. Every piece carries what it is · what goes in · what comes out · why it is shaped so · who it talks to · its observed state. Arrows are drawn only where the code actually calls; the one cable nobody plugs in today is drawn as a ghost.

This page holds no verdicts. Nothing here is approved or condemned; “is this how I want it?” stays open and is Sid’s. 1 · The story in fifteen lines

Plain words; the engine’s own names for things are in italics on first use and defined in §3. Nothing here needs a file name.

  1. A render engine has one job: take a description of what is on the page, turn it into pixels every time something changes, and say what is under the mouse.
  2. Here the description is one store. Every visible thing is a slot — a small tree of boxes already laid out, with its text, images, lines and 3D rooms flattened into plain arrays — keyed by what it shows (its address) and where it appears (its view-instance).
  3. Boxes sit in containers. A container is one six-number transform (move, scale, rotate). The transform is never baked into the boxes — it is one row in one table on the GPU, applied in the shader — so moving a container rewrites one row, not every box.
  4. Text is special. The shaper takes a line of text, a font and a width and decides once where every glyph goes (real shaping, word-wrap only at spaces and tabs). Everything downstream reuses that answer; nobody else measures.
  5. Everything drawn belongs to one of ten families — box, shadow, two kinds of text, clip, image, path, connector, chrome (selection furniture), 3D region. Each family is cut in two: a pure half that derives geometry from the store (it runs on the JVM in tests) and a GPU half that packs bytes and owns its shader.
  6. The store’s things become one ordered list — the tape — sorted by document-order data carried on each row (layer, pass, nesting path, rank), never by position in an array. Paint walks the tape forward; picking walks it backward, on the CPU, against box bounds.
  7. Each frame opens with one question per family: did any input you declared change since last frame? Only the families that say yes re-produce their rows; the rows merge into a kept, sorted arrangement.
  8. Change arrives as minted deltas — a row inserted or moved, a container changed, a region added, the viewport resized — minted by whoever made the change. Nothing scans the scene to discover what changed.
  9. One small reducer folds the deltas into the semantic state: which containers carry an effect (opacity, mask, blur) over which row ranges, and the frame plan (which passes draw into which textures). Every maintained view has a from-scratch twin — its oracle — it can be checked against.
  10. Then the GPU. Every drawable is the same unit square, instanced. Per-instance data (rectangle, color, corner radii, glyph uv, container row index) sits in a buffer; the vertex shader reads the container row and the camera and places the square; the fragment shader computes coverage — a rounded box by distance field, a shadow by a Gaussian, a glyph from an MSDF atlas or solved from its outline curves, an image by sampling.
  11. Two roads out. The legacy road opens one pass straight onto the canvas and walks the tape. The linear road goes through the compositor: the scene into a 16-bit-float texture, each effect group into its own texture, blur / mask / composite, then one present pass that converts to sRGB. A target pool leases those textures and refuses past a budget; blur degrades instead of dying.
  12. A scheduler decides whether a frame needs encoding at all — from causes (world, viewport, interaction, clock…) and registered deadlines — and time is handed in as a value, never read inside derivation.
  13. A 3D region is a whole 3D scene that appears as one row on the tape: its own camera, meshes, lights, shadows and depth, rendered into its own leased texture, then drawn as a quad like anything else; a pointer into it is routed to a resolver that picks inside.
  14. The verifier is a browser harness that builds the real systems, renders small cases twice, hashes the bytes against golden manifests, replays the scheduler, and runs source-level fences (“no family gets a private draw path”, “nobody measures text privately”).
  15. What is alive today: only the verifier drives any of it. The one function that does a whole frame has no caller — the product client that used to call it was cut at the waist — so this is an engine on blocks, proven by its harness, waiting for a host.
Sentences 2–9 are the CPU side (all of it pure, JVM-testable, except the atoms in the runtime). Sentences 10–11 are the GPU side. 12–14 are the edges. Everything here was read from source this session; the gatherer digests and line anchors are in §8.

3 · The words this page uses

slot
one view-instance’s whole render answer, precomputed: its laid-out tree of boxes (container-local), its flattened ops per family, its address index. Keyed by view-instance; a map value.
address · view-instance
address = what is shown (a block’s id); view-instance = which appearance of it (a face in a reader pane, the main face…). One address can appear in many slots.
container
a node in a transform hierarchy; one six-number affine [a b c d tx ty]; effective = parent ∘ local; carries a compact transport slot = its row index in the GPU table.
family
one kind of drawable. Ten: rect · shadow · msdf · slug · clip · image · path · connector · chrome · region-3d. Registered as data; no family gets a branch in the core walkers.
tape · entry · arrangement
the tape = the one ordered list of entries for a frame; an entry = one row (id · family · order tokens · paint pointer · pick policy · visibility); the arrangement = the tape as a kept sorted map, maintained by insert/remove between frames.
order tokens
the sort key carried on each row: stratum (world / overlay / region-composite) · pass class · nested stack path · part rank · stable tie. Document order is data, never array position.
delta
a minted change value: entry insert/move/remove · container (topology vs parameter) · region topology · global · region lease · region payload · viewport size. Minted by whoever made the change.
effect · span · plan
effect = a container-level compositing declaration (opacity · mask · layer blur · backdrop blur · isolate); span = the entry ranges a container’s effect covers; plan = the passes + resources for this frame.
maintained view · oracle · fence
maintained = updated incrementally from deltas; oracle = the same answer recomputed from scratch; fence = the check that the two agree (a test, or a flag-on twin check at runtime).
material half · GPU half
a family’s pure side (grammar, geometry, routing, tessellation — .cljc) vs its GPU side (pipeline, packed bytes, upload gate — .cljs).
road
the engine’s word for a code path you can choose between: legacy (one pass) vs linear (compositor); MSDF vs Slug for text; shaped vs legacy-monospace for layout.
receipt · golden · fence (.mjs)
receipt = a published measurement (ledger counters, plan hash, compositor stats on globalThis); golden = a rendered case hashed against a manifest; fence = a static check over the source text that forbids a class of regression.
PARKED · CUSTODY · LIVE
Sid’s word for this area (parked: guarded by the verifier build, no product entry) · kept only for TrailView / anatomy / goldens, one-cut deletion debt · has a runtime caller today.

A · Presentation grammar CUSTODY

workspace/face_assembly.cljc 31K · face_primitives.cljc 62K

What it is. The thing that turns “a face” — a block’s look, written as pure data — into a tree of boxes the scene store can lay out. A face is an assembly: nested maps of {:prim … :props … :children …}, {:each … :template …}, {:bind [...]}; no lists, no symbols, no logic — arrangement only. An interpreter walks it over a registry of 16 primitive builders and returns rect-tree nodes. It is kept only because TrailView, anatomy and the goldens still wear it; Sid has named it one-cut deletion debt.

How it works here. Two stages, deliberately: compile-assembly once at wear time (closures over the registry), apply-assembly at data-change time (compiled + data + view context → rt-tree). Frame time does nothing new. Both are total — a malformed assembly, an unknown primitive, a throwing primitive all resolve to a renderable error card carrying the assembly name, grammar version, address and the first five errors, so a bad AI-authored face lands as a card beside the chat, never a black screen. The primitives measure their own bounds bottom-up (“measure in the primitive, arrange in the engine”).

C · Scene values PARKED

workspace/scene_store.cljc 35K · rect_tree.cljc 35K · containers.cljc 12K · substrate/scene_tape.cljc 33K · selection.cljc 6K · snap.cljc 11K — all pure .cljc, every one with JVM tests

What it is. The description of what is on screen, as a value. No atoms, no GPU, no browser — the whole layer loads and runs on the JVM. Four ideas: the store (what is shown, where), the rect tree (how a thing is laid out into boxes and flattened into per-family arrays), containers (the transform hierarchy), and the tape (the one ordered list a frame draws from and picks from).

How it works here. A slot is one view-instance’s whole render answer, computed once at upsert: its resolved tree (container-local coordinates), eight flat op arrays (text · rects · shadows · images · regions · paths · connectors · chromes) with the container index already baked in, and its address → index-paths map so an address can be found without scanning. The store keeps {:slots :index :ordered}: slots by view-instance, an address→view-instances index maintained incrementally, and a sorted map of tape entries. Upsert/remove maintain the index and the order; nothing recomputes them by scanning at read time. Picking: bounds broad phase, children walked front-to-back, a per-family narrow predicate (path, connector, chrome bring real math; the rest say yes), then the hit path is bubbled leaf-first until a handler answers.

B · Scene runtime PARKED

workspace/scene_runtime.cljs 30K · chrome_runtime.cljs 17K · region3d_runtime.cljs 28K · frame_runtime.cljs 15K — .cljs, no JVM tests, zero callers except among themselves (and two receipt fns from the verifier)

What it is. The owner of the atoms. Everything in C is a value; somebody has to hold the current one, mutate it at the right moments, and hand derived views to the renderer. That is this layer: one store atom, one container-registry atom, a journal of container deltas, face lifecycle, the last pick, the action registry, and three Missionary views the (now deleted) product loop sampled. The chrome and region3d runtimes are the same idea for their own session truth; the frame runtime is the W4 fixture join.

How it works here. Mutations happen only at edges — user actions through a window API, the server echo fan-out — never inside a reactive derivation. Every container mutation mints a delta from the before/after declaration and appends it to a journal with a sequence number; consumers read a snapshot and ack a high-water mark. Face instances get a container id from a recycling pool (a monotonic counter walked into the GPU table’s ceiling after ~992 spawn/despawn cycles and killed the reactor — gate finding F3, 2026-07-13), the container is added first, then the slot. The three views: <store-frame (one m/latest over the store → the GPU payload), <effective (→ effective transforms), <frame-registry (→ plan-layer topology + effects). The file still names its old consumers — render.cljs, mouse.cljs, face_wiring, agent_flow — none of which exist any more.

D · The shaper PARKED-but-floor

workspace/text_layout.cljc 73K · text_layout_planes.cljc 25K · text_shaper.cljs 14K · runtime/fonts.cljs 13K — text-layout tests + shaping-correction test + two static fences green

What it is. Text in, placement out. One entry, layout, takes text + font + size + line height + width (or a wrap column) + a layout key and returns one immutable, versioned value: lines, each with its baseline, advance, logical and ink bounds, glyphs (id · position · advance · cluster → source range), clusters, runs; plus metrics, a clip plan, receipts. Seven readers (measure · wrap · paint · caret · selection · clip · hit-test) read from that value and echo its id, so a consumer can prove which layout it read. Nobody else measures — a fence over the source forbids private metric arithmetic anywhere in src/app.

How it works here. For each source line the provider shapes the whole line once (HarfBuzz in wasm, with bidi); the layout then walks the clusters left to right accumulating advance until the width is exceeded, remembering the last whitespace run — that run is the cut. Only SPACE and TAB are break opportunities (never a \s class, so NBSP never breaks); if nothing fits, a hard cut at one cluster (an emoji stays whole). The whitespace is consumed (owned by the line, painted as nothing) so copy still returns it and the caret can sit in it. Widths are HarfBuzz advances in font units — never Canvas2D measureText. A wrap column is turned into a width by shaping a single space once and multiplying. The pure layout never measures: the provider is injected as a plain function, so the JVM tests run it with a synthetic one. Results are compacted into planes — columnar typed arrays — and glyph/cluster maps are rebuilt at the accessor boundary: retaining them cost ~150 MB on a 228k-glyph boot (measured 2026-08-08).

How it works here — one frame, in order. How it works here. There are no vertex buffers of geometry at all: every pipeline draws (6, N) — six corners of a unit square from vertex_index, N instances — and the one vertex-buffer slot carries per-instance data (stepMode "instance"). A rect instance is 116 bytes (28 floats + a container u32: geometry · color · corner radii · border widths · border color · gradient); a shadow 84; an MSDF glyph 52 (rect · uv · color · container); a Slug glyph 100 (rect · sample bounds · inverse Jacobian · banding · glyph location · color · container).
