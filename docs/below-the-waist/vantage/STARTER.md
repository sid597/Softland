# STARTER — the vantage round's builder (Sid's own words, spliced 2026-09-08)

Two complete prompts, ready to paste as the first message of a fresh session. One per lane. The Fable lane's worktree exists: `/mnt/data/projects/Softland-vantage`, branch `waist/vantage-claude`, off main at the commit that carries `MILESTONES.md`.

## Fable builder — paste whole

```
preflight: permission mode and toggles set before this first prompt, nothing mutates mid session. fable, effort max. you are in the worktree /mnt/data/projects/Softland-vantage on branch waist/vantage-claude, off main; src/ and test/ in scope, read and write; never src/app/server/env.clj.

ok so the 3d and path work is done and for the last few sessions i have been asking myself what to do next. i ran that through several sessions and then sat with one to find the minimal layer we can build on top of the existing code. this is all supposed to be done on an ecs layer and we don't have it: the anatomy of what is on screen as data, so i can stand in front of it and change it, and so my agents can. we found it and wrote it down as milestones, and now it is money where mouth is. build it, in a separate worktree, and once the builds exist we arrive at the next layer to build.

what i'm building is every tool, 2d and 3d, as data above a waist of code that exists once. humans and agents should be able to create, edit and reuse the tools themselves. one window where i can think and work through different representations of the same subject, and as you zoom in and out the subject and context change while some things stay pinned. chemistry is the breadth; this should make sense for software, teaching, games, engineering, and fields we haven't thought about yet. the first subject is softland itself: its codebase, how the architecture is implemented, how the pieces map together, how a change travels through it, and how the agents see and work through it, since they do so much of the reading and changing. there is much we can do with softland using softland. there is value in all three layers, text, 2d and 3d, to see the flow of the architecture live and analyse it. the work we do in these chats should start having a place inside it.

i tried an earlier version of this and it failed badly. i lived in the blocks: type a thought, ctrl+enter, see the reply under it, types by hand like #TASK. then i wanted to change the block itself, small things: a paste from outside should take at most half the space, ctrl+enter should show which model, what effort, how much precontext, replies should attach differently. and i hit a wall. there was no place to stand in front of how the thing is made and evolve it. the anatomy of the block was code. the views we built of it were true and useless to me, the wrong level, like being shown the rama module. typing got slower the more i wrote, click and cursor disagreed. so i stopped and built the engine.

the layer, in the words the milestones use: a vantage, what i stand in front of, a record that says what i look at, through which tools, what is pinned, at what zoom, who is looking and where i came from. layers, one asserter's possibility over the shared store, promotable. the text tool as a record with roots and a program, the way the path and 3d tools already are. the agent's turn as a record i read before it runs. the pointer and the loop. then the map: softland's architecture from the code records, drawn by the path and 3d tools in the same vantage. docs/below-the-waist/vantage/MILESTONES.md has the six milestones, what i see at each, what exists under each with file and line, and the positions the chair took with their exits. they are checkpoints, not a contract. they may change as you build and that is fine, but i should know: the file changes in the same commit as the code. the current client is so bare that you will have to build a few base components; i want to see them as the checkpoints.

what exists, graded. the executor, the compositor and the path and 3d tools are code with jvm tests; a tool record is roots and a program, and the harness edits a root and reruns; tested, not live. text is code: one pure layout function that returns lines, runs and glyphs, with caret and hit test as functions over its result, its own gpu draw, nothing samples it, no tool record. the store holds my history as rows: containers with revisions, relations with the asserter inside the identity, an agent's turn written as a row before the agent runs; model and effort go from the invocation facet into the spawn arguments and a printed line, not the row; the prompt is composed in code at that seam. a record comes back as a document after its first edit. two layer stubs that nothing reads. the nearest thing to a vantage is a camera cell per world. the code import and the transcript import exist and are tested, and the server boots against a rama conductor by default or in-process with LAND_CLUSTER=0, with the ingest sweeps on that boot path; no cluster is running right now, so what is in the store is what the boot you run puts there. there is no page a person opens: the client runs only under the verifier's puppeteer with swiftshader, no html, no watch build, no keyboard handling anywhere. no route returns a thread or a container's revisions to a client; the conversation face exists as a function with no caller. no pointer, no wire, no loop.

you are the best at ui so i expect whatever you make to be quite high quality. this is the client i will work in, not a bench.

how i work: the prototype is the spec, no contracts. you build the tests as you build. the docs are the hierarchy from the readme to the docstrings to the code, changed in the same commit. functional. the data layers, the data flow and the reactive question worked out early. how the best team in the world for this would do it. one commit per milestone on the branch by exact path; push and merge are mine. the process is docs/below-the-waist/two-chairs.md.

things i hold: when you see the ceilings do not try to hack through them, we want to build through them. caching is never an option, it means the underlying thing is as it should be and then still need more performance therefore we need to do caching on top. the data should be saved as it is. best in field is a datapoint; nothing is carried forward for existing. and be anal about what exists exactly; we deviate from what is true the moment we say "works" about something we only read.

whatever i say take it as a bit of approximation; some answers have to be filled by you yourself. once you get to a state where you tried everything and cannot build forward, write me up what you were going to build, what all you tried, where you are, and what is the missing critical piece that needs my approval, as docs/below-the-waist/vantage/ASK-N.md, and stop there.
```
