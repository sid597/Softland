  Paradigm Analysis: Pull-Based Interaction Layer

  What the current architecture actually is

  From the code, the system is an explicit hybrid (CLAUDE.md already
  acknowledges this):

  Render path (pull, continuous synchronous):
  atom watches → m/latest world snapshot → m/sample on RAF → GPU draw

  Interaction path (push, event-driven):
  DOM events → m/observe → m/eduction filter → m/reduce → atom mutations
  (reset!, swap!)

  Your proposal: unify these by making the interaction path pull-based too —
  handlers only fire when RAF samples them.

  Failure modes

  1. Discrete events have no "current value"

  This is the fundamental problem. Missionary's type system distinguishes:
  - m/watch = continuous flow (atoms always have a value)
  - m/observe + m/relieve = discrete flow (events that happen)

  A keypress for 'a' is an occurrence, not a state. It doesn't have a "current
  value" to sample. To make it continuous, you'd need to buffer events into an
  atom — but then push is still there, just hidden behind an extra indirection:

  ;; This doesn't eliminate push — it relocates it
  DOM keydown → push to buffer atom → m/watch buffer → sample on RAF → process

  2. Lost keystrokes under load

  At 60fps, RAF ticks every ~16ms. If a user types "abc" within one frame
  (normal typing speed), a pull model that samples "keyboard state" would only
  see the last key held. You'd need an event queue, which means you're doing
  push-with-batching, not pull.

  3. Paste handler is physically impossible to defer

  mouse.cljs:29 — .preventDefault e must run synchronously during the DOM event
  callback. If you defer to RAF, the browser's default paste has already
  executed. Same issue with drag-select's coordinate capture.

  4. +8ms average latency on every keystroke

  Current: event → atom mutation (sub-ms). Proposed: event → wait 0-16ms for RAF
   → process. This is perceptible in a text editor. Even game engines process UI
   input outside the main loop.

  What paradigm this maps to

  The proposal maps to Lustre/Esterel synchronous clocked computation — all
  state transitions happen at clock ticks (RAF). But Lustre was designed for
  continuous sensors (temperature, position) that naturally have a "current
  value." Keyboard events are fundamentally asynchronous discrete events —
  fitting them into Lustre requires an event queue, which reintroduces push
  semantics under the surface.

  Why the hybrid is actually correct

  Van Roy's taxonomy separates two concerns:
  - Observation model: How do you learn about changes? (Push vs Pull)
  - Computation model: How do you derive state? (Eager vs Lazy)

  Softland's current split:

  ┌─────────────┬───────────────────────────┬───────────────────────────────┐
  │    Layer    │        Observation        │          Computation          │
  ├─────────────┼───────────────────────────┼───────────────────────────────┤
  │ Interaction │ Push (DOM events → atom   │ Eager (handlers fire          │
  │             │ mutation)                 │ immediately)                  │
  ├─────────────┼───────────────────────────┼───────────────────────────────┤
  │ Render      │ Pull (m/sample on RAF)    │ Lazy (derived flows recompute │
  │             │                           │  on demand)                   │
  └─────────────┴───────────────────────────┴───────────────────────────────┘

  This is correct because:
  - You can't pull keyboard events — the browser pushes them. m/observe wraps a
  push API.
  - You should pull derived state — no point recomputing tokenization 5 times
  between frames if 5 keystrokes landed.

  The "two paradigms" aren't an inconsistency. They're Gary Bernhardt's
  Functional Core, Imperative Shell: imperative event handlers mutate atoms (the
   shell), continuous flows derive everything else (the core). The atoms are the
   membrane between paradigms.

  What would be a real improvement toward unification

  If you want more paradigm consistency without the failure modes:

  Option A — Thinner handlers, richer flows. Instead of computing hit-testing
  and coordinate conversion inside push handlers (handle-mousedown! does layout
  resolution, coordinate math, fold toggling — 100+ lines of push-side
  computation), emit raw intents:

  ;; Push side: emit intent, nothing else
  (reset! !intent {:type :click :pixel-x x :pixel-y y})

  ;; Pull side: continuous flow interprets intent in the render path
  (m/latest (fn [intent viewport scroll-y layout ...]
              (resolve-click intent viewport scroll-y layout))
            (m/watch !intent) (m/watch !viewport) ...)

  This moves computation from push to pull without losing events. The handler
  becomes a thin relay.

  Option B — Event log reduction. Instead of (swap! !editor-doc assoc :cursor 
  pos), emit {:type :cursor-move :pos pos} to an append-only event log. A
  continuous flow reduces the log into editor state. This aligns with the Rama
  event-sourcing vision from the moonshot doc — the event log is primary,
  rendered state is projection.

  Both options keep push where it's unavoidable (DOM event capture) but move the
   semantics into the continuous synchronous world.

  ★ Insight ─────────────────────────────────────
  The key distinction is between event capture (inherently push — the browser
  controls timing) and event interpretation (can be pull — you control when to
  derive meaning). The current code does both in the push handlers. Separating
  capture from interpretation would give you 90% of the paradigm unification
  without the latency and correctness costs of polling input state.

  This maps to Missionary's own type distinction: m/observe for capture
  (discrete), m/latest/m/sample for interpretation (continuous). The atoms
  bridging them aren't a hack — they're the correct seam between discrete
  observation and continuous computation.

  Electric IS the Differential Pipeline

  diffs with six operations:

  {:grow        3          ;; 3 new slots appeared
   :degree      8          ;; total size after growing
   :shrink      0          ;; 0 slots removed
   :permutation {0 2, 2 0} ;; items at 0 and 2 swapped
   :change      {5 :new-a  ;; slot 5 got a new value
                 6 :new-b
                 7 :new-c}
   :freeze      #{3 4}}    ;; slots 3,4 are final (optimize away)

  From the old code AND the mount_impl source, here's what the full model looks

  ;; THIS IS ONE PROGRAM. Not five layers.

  (e/defn world-view [rama-pstate]
    (e/server
      ;; Watch Rama PState — server side
      ;; When topology updates PState, this AUTOMATICALLY fires
      (let [all-nodes (e/watch rama-pstate)]

        (e/client
          ;; Data arrives on client via websocket — NO API
          ;; Electric handles the transfer

          ;; Filter to viewport (client knows camera position)
          (let [visible (viewport-cull all-nodes camera)]

            ;; - diffs visible collection by :id
            ;; - ONLY runs body for ADDED/CHANGED nodes
            ;; - AUTOMATICALLY cleans up REMOVED nodes

              ;; This runs ONCE per new node
              ;; When node updates, only this node's body re-runs
              ;; When node leaves viewport, on-unmount fires
              (gpu/update-buffer-slot! (:id node) node)

              (e/on-unmount

            (gpu/present-if-dirty!))))))

  - The PState change flows from Rama → server → client → GPU without any API

  He dropped the ring.

  The whole piece is structured as a PIPELINE:

  pressure → local world → move → trace → artifact → projection → new pressure

  But he never closes it explicitly. It IS a loop — "new pressure / refined

  ring.

  This matters because a pipeline implies a direction (input → output). A ring

  insert thought
  link evidence to claim
  fork trail
  accept synthesis

  - A topology processes a new event and updates a PState → the world changed,
  but nobody "made a move"
  - An LLM's internal reasoning produces an intermediate conclusion → not a
  committed move, but not a raw signal either
  - The user scrolls and a new cluster of nodes enters the viewport → the

  signal → gesture → proposal → candidate move → committed move → traced move

  Codex has: signal → (interpretation) → candidate move → committed move. But
  "interpretation" is doing a LOT of work in that pipeline. The personal AI, the
   system's own heuristics, the workflow context — they all participate in
  turning a signal into a candidate move. That's not one step. It's a whole
  subsystem.

  Minecraft is a recursive world. Smalltalk is a self-modifying world. Croquet
  is an event-sourced world with inhabitants. What makes Softland different from

  it's this: Softland is a world where the primary material is understanding,

  Softland, you manipulate UNDERSTANDING — claims, evidence, tensions,

  The Diff Compounds Across Layers

  This is the key part. It's not just one layer diffing — EVERY layer receives
  diffs and emits diffs:

      RAMA                    ELECTRIC                WEBGPU
      ═════                   ════════                ══════

      1000 nodes              "150 entered            "add 150 rects
      in PState               viewport"               to buffer"

      new event               e/diff-by               mount callback:
      appended                computes                append-child
           │                  structural              (:grow 150)
           │                  diff:                        │
           ▼                  {:grow 150                   ▼
      topology                 :shrink 0              GPU allocates
      processes               :permutation {}         150 buffer slots
      ONLY the                :change {50 nodeA       uploads 150 rects
      new event                        51 nodeB       ONLY
      (incremental)                    ...}}
           │                       │                       │
           ▼                       ▼                       ▼
        Δ ──────────────→ Δ ──────────────→ Δ ──────────→ draw

      The ENTIRE pipeline is  Δ → Δ → Δ → Δ

      No layer ever sees the full 1000.
      Each layer processes only what changed.
