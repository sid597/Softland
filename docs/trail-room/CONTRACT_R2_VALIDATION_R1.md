## Blocking findings

### B1 — G1 demands cross-band bounds identity, which is geometrically impossible and contradicts the R-1 as-built resolution of trap 6

**Contract cite.** §4 G1 (CONTRACT_R2.md:151-154): "band 1 → EXACTLY one text op…; band 2 → exactly two line ops; band 3 (open) → the surface node with bg. **The node's bounds are IDENTICAL across bands 0–3** (trap 7)." Trap 7 (:126-129): "rt-node bounds unchanged **at every band**; only ops differ." §1 item 1 (:23-24): "rt-tree node bounds unchanged, paint only (R4)."

**Authority/code cite.** A node holding 1 text line (band 1), a node holding 2 lines (band 2), and the open **surface** (band 3 — design R5 lists "full clocks, badges, verdict lines… omissions block, material preview… address", room-card-lane:96) cannot share identical bounds; the open expansion is dozens of line-heights tall. The as-built card height is *derived from line count*: `h (+ (* (count lines) lh) 8)` (cards.cljc:287). R-1 already ruled the opposite of "identical": PHASE_R1.md's cards.cljc note records "**Hit bounds shrink WITH the paint** (trap 6: paint/bounds stay consistent, click still lands)" — i.e. bounds *track* paint, they are not invariant. Design R4 (room-card-lane:79-86) wants the hit region to equal *the full line region at that band* (paint may be smaller, e.g. a glyph), not one height across all bands.

**Why both cannot hold.** If bounds are pinned identical across bands, band 0 (a single glyph, the whole point of which is a dense 167-row overview) must occupy band-2 (or band-3) height, destroying the compression the bands exist to deliver — and band 3's surface can't shrink to a glyph line. The literal gate can never be made to pass; the charitable reading (pin all closed cards at band-2 height) contradicts R-1's shipped "bounds shrink with paint."

**Smallest fix.** Re-scope trap 7 / G1 to *per-band* consistency: "at each band the hit-region node bounds equal that band's painted line-region (so the click target matches the paint — R-1 trap 6); bounds MAY differ across bands (band 0 is densest). The open card's expansion is a SEPARATE sibling node; only the title/handle node is the closed-card click target." Assert equality of hit-node bounds and paint region *within* a band, and that the click still lands — not cross-band identity.

### B2 — §2.5 / G7's "permuted-input" assertion is incoherent against the arrival-sorting builder, and its "consume in the order given" clause contradicts §2.5's own order-as-data purpose

**Contract cite.** §2.5 (:93-101) + G7 (:173-178): "the scene builder **consumes `:feed/entries` in the order given** (assert the builder output for a permuted-input copy of the fixture **differs ONLY in y-stacking derived from the order** — i.e. no API re-sorts as a side effect)." Trap 3 (:105-115) frames the goal: order must not ride the sequence.

**Authority/code cite.** The builder does NOT consume the given order — it sorts by the arrival-ms (or claimed-ms) DATA field first: `sorted (vec (sort-by … entries))` (scene.cljc:416-421), then `assign-lanes` runs over `sorted` (scene.cljc:424-425). `assign-lanes` defines lane index = order of first appearance in the passed seq (lanes.cljc:47-66). Fixture arrival-ms are all distinct (feed.edn: …171/172/169/168.5/166 e9), so the arrival sort is a *total* order → a permuted `:feed/entries` is canonicalized back to the identical `sorted` seq → **byte-identical scene**, not "differs only in y-stacking." The gate as worded therefore cannot be executed to pass: there is no y-stacking difference to observe.

**Why both cannot hold.** The two halves of §2.5 are mutually exclusive: "consumes `:feed/entries` in the order given" (trust raw sequence, no re-sort) versus "thread index computed as per-entry ATTRIBUTES… order must not ride the incseq." If the builder honored "order given" and dropped the sort, `assign-lanes`' lane index would ride raw sequence position — exactly the permutation-diff hazard §2.5 exists to forbid. The only way lane index becomes an *attribute independent of sequence* is to derive first-appearance from the arrival-ms DATA field, i.e. to sort — which "consumes in the order given" forbids. So the contract demands order-independence from an order-DEFINED function while simultaneously forbidding the one operation (sort on arrival-ms) that makes it order-independent.

**Smallest fix.** Replace §2.5/G7's "consumes `:feed/entries` in the order given / differs ONLY in y-stacking" with: "the builder derives every position from the **arrival-ms attribute** (canonicalizing by sort on that field); raw `:feed/entries` sequence position is never load-bearing. Assert: (a) a permuted-input copy yields a **byte-identical** scene; (b) thread/band membership + in-thread index arrive as node DATA (`:trail-face/thread`, `:trail-face/band?`) on every entry node; (c) assignment/move APIs return entry-key/target-id-keyed maps, never a re-sorted entry seq."

## Should-fix findings

### S1 — §5 allowlist mislocates the trail view-state owner; the `/trail band` dispatch file is unlisted
§5 (:191-200) names "`workspace_actions.cljs` / `editor_compute.cljs`" as the expected view-state owner. Neither owns it. The trail view-state atom is `:!trail-face-state` (state.cljs:198); `/trail` commands mutate it in **agent_flow.cljs:311-318** (`:off`/`:order`/`:set` case), expansion toggles in **mouse.cljs:404**; the pull loop reads it in **wiring.cljs:39-60**. `workspace_actions.cljs` only *reads* `:face` (:147); `editor_compute.cljs` only *watches* it (:388). The new `/trail band <0|1|2>` op (§2.2) must be applied in the agent_flow.cljs case block — a file that is neither in the allowlist nor in UNTOUCHED. §8's "view-state location differing… locate + name it" saves this from being blocking, but the allowlist should name `state.cljs` + `agent_flow.cljs` (+ `wiring.cljs`/`mouse.cljs`) rather than misdirect.

### S2 — §2.4 "prev-assign carried in the trail view-state" loops against the as-built wiring
§2.4 (:85-91) says the previous-pull `{target-id → thread}` map is "carried in the trail view-state." If placed literally in `!trail-face-state`, every per-build write to it fires **wiring.cljs:60** (`add-watch !trail-face-state … (request!)` → a re-pull) and re-triggers **editor_compute.cljs:388** (`m/watch !trail-face-state` → scene rebuild). That is a rebuild/re-pull feedback loop, and the write-back would sit inside the `<trail-face>` `m/latest` (a CLAUDE.md "no side effects in m/latest" hazard). No gate covers this (G6 tests only the pure `moves` fn; W-1 is a screenshot). Fix: store prev-assign in a **separate cache atom** (the `!last-trail-struct` pattern, editor_compute.cljs:351), not `!trail-face-state`; state the write is a post-build cache, not a watched input.

### S3 — connected-components × family-key fold interaction is under-specified; "member" for the lex-min identity is not defined
§1 item 5 (:25-34) makes lanes = connected components over lineage edges (endpoints are target-ids) AND makes family-key a vertical fold (doc + `du:` blocks → one card). It never says which wins when a `du:` block has its *own* lineage edge putting it in a different component than its folding doc — two physically different lane assignments result. §2.3 (:76-83) keys thread identity on the "lexicographically-smallest **member** target-id," but "member" is undefined for folded entries, and `du:…` ids sort *below* `oc:…` ids (`d` < `o`), so a thread's identity could be pinned to an invisible folded block — deterministic but surprising and unstable if that block later gains its own edge. Fix: define "member" as the visible-card / edge-endpoint target-id set explicitly, and state fold-vs-component precedence (recommend: fold first, then assign the folded unit by the *doc's* edges).

### S4 — trap 4 bans lane mod-wrap but doesn't scope the replacement overflow mechanism
Trap 4 (:116-119) rules "threaded lanes never wrap" (removing the F-L2 staircase fix's mod-wrap, lanes.cljc:67-70 / scene.cljc:424-425). Design R7's overflow default (room-card-lane:159-160) pairs that removal with "more threads than viewport lanes → **fold-chips with counts**." The contract takes the removal without scoping the fold-chip replacement. Over the real corpus (the §10 first-light gauge) many threads would then staircase off-screen — the exact F-L2 bug returns. Fix: scope thread-overflow → fold-chips (or explicitly defer it and cap thread count for this tranche).

### S5 — band-0 staleness dot needs attestation data the feed does not carry
§1 item 1 / G1 specify "band 0 = glyph + staleness dot." `staleness-treatment` needs `:times {:last-attested-ms}` (cards.cljc:106); feed entries carry only `:time/claimed-ms` / `:time/arrival-ms`, no attestation (`:times` lives on the per-target *bundle*, pulled only for expanded cards). Attestation/walk is D-008 §5, which §1 lists as NOT in scope (:52). So band 0 is buildable as glyph + fold-count only this tranche; the dot cannot be sourced. Fix: state band-0 renders glyph (+ fold count), staleness dot deferred with the attestation walk.

### S6 — G6 asserts the reason "names the far-end display-name," but relation-transition targets carry none
G6 (:169-172) requires the move reason to name "kind + far-end display-name." The fixture's relation-transition targets carry no `:display-name` (feed.edn:6-10 + confirmed: only `source-ingested`/`transcript-file-updated` targets have it). §7 duty 6 (:239-240) says fall back to the raw id when absent. The gate and the duty disagree. Fix: either add a display-name to the produced edge's far end in the extended fixture, or reword G6 to accept "display-name when present, else raw id" (matching the duty).

### S7 — band geometry silently substitutes "reading order = time" for the design/ledger's binding "x = time" law
See scenario trace D/F. The contract (§1 item 5:33) sets "reading order = time order"; the design (room-card-lane R7:145 "x = time preserved (LAW: x is time everywhere)") and the do-not-preclude ledger ("x = time (given), y = lane… opening detail costs local space, never the shared axis") declare x=time binding — while the as-built is y=time/x=lane (axes swapped, scene.cljc:439-447). The contract neither honors nor flags this. Fix: state explicitly that R-2 builds on the y=time F-L5 stack and defers the x=time/y=lane geometry as a do-not-preclude item (rather than silently redefining the design's law).

## Scenario traces (A–F)

**A. Are G1–G11 JVM-executable over the pure cljc core with the fixture idiom?** Mostly yes, with two exceptions and several fixture extensions:
- Executable as-is: G2, G8, G9 (= R-1's G4 forms), G10, G11 (JVM/shell).
- **G1 — NOT executable as written** (B1: impossible cross-band bounds identity).
- **G7 — NOT executable as written** (B2: the sorting builder absorbs permutation → identical output, contradicting "differs only in y-stacking").
- Executable *only after fixture extension* (sanctioned by §7 duty 4): the feed carries lineage kinds `based-on ×1`, `dead-end ×1`, `confirms ×1` and no `produced/built-over/new-direction/references/elaborates`. So **G3** (3-commit based-on chain + 2 unedged docs) needs added terrain entries + chain edges; **G4** (a `:references` cross-link between two threads) needs a `:references` relation-transition entry (none today); **G5** (doc + `du:` blocks fold to one card) needs *terrain* doc+block entries (today both `oc:doc:9fdoc` and `du:9fdoc:000003` are relation-transition marks, not cards, so the fold has nothing to fold); **G6** needs a `:produced` edge and — to satisfy "names the far-end display-name" — a display-name on that far end (S6). The `:relation-transition` detail shape does carry `:from/:to/:kind` for connected components (feed.edn:23-25), so components are buildable; the gap is *coverage of kinds and terrain cards*, not shape.

**B. §2.3 merge scenario — do chips fire only for the changed side?** Trace: Thread A={m,p} (id=min="oc:doc:m"), Thread B={a,z} (id="oc:doc:a"). New `based-on` joins p∈A and a∈B → union {m,p,a,z}, id=min="oc:doc:a". prev-assign {m→m, p→m, a→a, z→a}; new-assign {m→a, p→a, a→a, z→a}. Changed = {m,p} (the A side, which did *not* contain the global min); unchanged = {a,z}. So `moves` fires chips for m,p only — **correct, only the side that changed announces** (§2.3 holds, §2.4 diff is a keyed map, no queue). **But "smallest member id" is NOT cleanly well-defined once folds enter** (S3): if the component contains a folded `du:` block target-id, it sorts *below* the doc's `oc:` id and would become the thread identity though it renders inside the doc card; and whether a band-bound block that folds into a threaded doc "joins" that component is unspecified. Recommend defining "member" as the visible/edge-endpoint target-id set and excluding folded members from the identity min.

**C. Is G7's permuted-input assertion meaningful?** No — this is B2. `assign-lanes` is order-DEFINED (lane = first appearance, lanes.cljc:48-66), and the builder canonicalizes by sorting on the arrival-ms attribute (scene.cljc:416-425) before calling it. A permuted `:feed/entries` therefore produces a *byte-identical* scene, so "differs ONLY in y-stacking" is unobservable, and the alternative reading ("consume in the order given," no re-sort) would make lane index ride raw sequence — the very hazard §2.5 forbids. The contract accidentally demands order-independence from an order-defined function while forbidding the sort that supplies it. Precise rewording is in B2's fix.

**D. Is "reading order = arrival order" + "x = time preserved" (R7) simultaneously satisfiable in the current geometry?** No, on two counts. (1) The as-built timeline is a *vertical* stack: y = time (sorted y-cursor), x = lane indent (scene.cljc:439-447) — the axes are the **opposite** of design R7's "x = time" / the ledger's "x = time (given), y = lane." "x = time" is not preserved anywhere in the current geometry. (2) Even within the band, "x = time preserved" and "wrap-packing" are mutually exclusive — wrapping to a new row resets x, so x can't encode a monotone timestamp. The contract quietly resolves both by dropping x=time to "reading order = time order" (§1 item 5:33). That is a reasonable engineering choice on the y=time stack but **under-specifies relative to the design's stated LAW and silently overrides it** (S7). The contract should name the substitution and record x=time as deferred/do-not-preclude, not present "reading order = time" as if it satisfied R7.

**E. Does the §5 allowlist cover item 6's "since last pull" (prev-assignment) state? Where does trail view-state live?** The allowlist is **insufficient and mislocated** (S1). Trail view-state lives in `!trail-face-state` (state.cljs:198), mutated by `/trail` in agent_flow.cljs:311-318 and by expansion in mouse.cljs:404, consumed by wiring.cljs:39-60 (pull) and editor_compute.cljs:352-390 (scene build). The allowlist's "expected `workspace_actions.cljs` / `editor_compute.cljs`" is wrong (the former only reads `:face`; the latter only watches). The `/trail band` op needs agent_flow.cljs (unlisted); prev-assignment needs a new atom in state.cljs. And §2.4's "carried in the trail view-state" is actively hazardous if taken literally (S2): any write to `!trail-face-state` re-fires wiring.cljs:60 (re-pull) and editor_compute.cljs:388 (rebuild). The correct home is a separate cache atom written post-build. §8's stop-clause makes the *location* implementer-fixable, but the allowlist and §2.4 as written would misdirect a builder into a loop.

**F. Does anything reopen a CLOSED decision or violate the do-not-preclude ledger?** No CLOSED decision is reopened: D-008 read-only holds (no kernel/server writes; move detection is client-side and defers persistence to D-008 §5, §2.4:90-91); D-001 is cited correctly (band palette command as daily-use fuel, threads client-side promoted only on form-break — :64, :72); D-005 grounds the client-side thread pass (:60). The move-chip "since last pull" is a per-card keyed flag, not an "arrival-ordered queue surface," so it does **not** violate the ledger's "'what's new' is a walk… must never require an arrival-ordered queue surface" — it is the labeled interim, and it precludes the future walk. The band rule (lineage lanes / family fold / unthreaded → visible band, never auto-filed/hidden) matches the ledger's "ungrouped threads render as a visible band — never auto-filed, never hidden" exactly. The **one** live tension with the ledger is geometric: the ledger's "x = time (given), y = lane… never the shared axis" is a binding-narration law that the as-built (y=time/x=lane) already inverts and that the contract builds on without flagging (S7) — a do-not-preclude concern, not a reopened decision.
