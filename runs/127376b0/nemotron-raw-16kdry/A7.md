\[
\boxed{\text{Decision‑log > Contract > Sessions Baton}}
\]

**Why this order?**

| Document | Why it outranks the others |
|----------|---------------------------|
| **Decision log** (`docs/current‑mental‑model/decisions.md`) | – Closed decisions are *explicitly* marked “CLOSED” and are the only mechanism that can *modify* a binding contract (see the “Authority note” in every contract file, which cites `decisions.md` as the ground‑truth). <br>– A decision can add, remove, or amend the obligations encoded in a contract, so it holds the highest authority to change the scope of a build package. |
| **Contract** (`build/*/CONTRACT.md`, e.g. `build/trail‑view/CONTRACT.md`) | – Declared **BINDING** (status = “BINDING” and countersigned by Sid). <br>– It is the *operational specification* for the build (what must be implemented, which gates must pass, file allow‑lists, etc.). <br>– It can only be altered by a formally closed decision; otherwise it remains the definitive scope for the current work package. |
| **Baton** (`docs/sessions/next‑prompt.md`) | – A session‑level instruction that **“supersedes everything below”** (see the BATON file). <br>– It tells the team *what to work on now* but does **not** have the power to change the contractual scope or to override a ratified decision. <br>– Its authority is limited to the current execution context; it must be consistent with the contract and with any governing decision. |

**In practice:**  

1. A *closed decision* (e.g., a change to the contract’s gate list) can rewrite the contract’s requirements.  
2. The *contract* then becomes the authoritative source for what the build package must deliver.  
3. The *baton* merely directs the team to start work on that contract; it can be updated freely but cannot override the contract or a binding decision.  

Thus, when conflicts arise, the hierarchy of precedence is **Decision log → Contract → Baton**.
