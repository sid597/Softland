# Knowledge Earth ZUI - Category Theory Design Research

Status: big-vision design research synthesis, 2026-06-08.

This is the broader research track beyond import/source preservation. The
import-facing view asks how outside material becomes trustworthy Softland-native
terrain. This note asks the bigger question:

```text
Once inside Softland, how do people and AIs navigate, absorb, translate,
simulate, dispute, synthesize, and build on knowledge across scale?
```

## Hard Verdict

The import research was right, but narrow.

```text
Source-to-World
  = can outside material become trustworthy Softland terrain?
```

The larger Softland design problem is:

```text
World-to-Understanding
  = can a mind enter a body of knowledge, construct the right mappings,
    manipulate models, preserve disagreement, synthesize, and contribute?
```

Category theory is not a visual style and not merely a backend formalism. For
Softland, category theory is the design grammar for:

```text
objects
relations
translations
worldviews
context changes
zoom levels
composition
gluing
disagreement
synthesis
learning
handoff
```

The central design primitive is not only an object or a graph node.

It is the arrow.

## The Arrow Softland Cares About

The user named the important arrow:

```text
knowledge that exists
  -> human or AI trying to absorb and build on it
```

This is not a simple information-transfer arrow.

It is a structure-building arrow.

The learner does not merely receive facts. The learner constructs a map from
one world of meaning into another:

```text
source world
  terms, claims, models, evidence, practices, open problems

learner world
  prior concepts, metaphors, examples, questions, tools, goals

learning arrow
  a structure-preserving translation that makes the source inhabitable
```

Design consequence:

```text
Softland should not only show knowledge.
Softland should show the maps by which knowledge becomes usable by a mind.
```

## What Ologs Add

Spivak's ologs treat an ontology as a category:

```text
boxes
  types of things

arrows
  aspects / relationships / functional descriptions

paths
  composite meanings

commutative diagrams
  claims that two paths of meaning agree
```

The key design insight is not "make boxes and arrows."

The key design insight is:

```text
An ontology is a worldview with testable paths.
```

If two experts describe a domain differently, they may not merely disagree on
facts. They may inhabit different ologs: different objects, different arrows,
different path equivalences, different assumptions about what composes.

Softland should therefore support:

```text
worldview as inspectable structure
translation between worldviews
visible path disagreement
repair of broken mappings
synthesis as new structure, not summary
```

## What Topos / Collective Intelligence Adds

Topos Institute's collective-intelligence work points toward compositional
thinking for many minds and systems:

```text
individual models
  partial, situated, domain-specific

interfaces
  ways those models communicate and compose

collective intelligence
  not one giant mind, but many partial intelligences whose structures can be
  aligned, compared, composed, and improved
```

Design consequence:

```text
Softland collaboration is not shared cursors.
Softland collaboration is model alignment, model conflict, and model synthesis.
```

The product should make visible:

```text
who holds which model
which arrows align
which diagrams fail to commute
which translations lose information
which conflicts are productive
which synthesis actually improves the collective model
```

## The Big Research Correction

The import view says:

```text
show transformation without lying
```

The full Softland view says:

```text
show composition without flattening
```

This is bigger.

When the user is already working inside Softland, source provenance becomes
background geology. It is still recoverable, but it is no longer the main task.

The main task becomes:

```text
which models are in play?
which scale am I at?
which arrows can I follow?
which arrows can I construct?
which diagrams are coherent?
which diagrams are contested?
what can I simulate?
what can I replay?
what can I contribute?
```

## Categorical Concepts As Design Primitives

### Object

Math:

```text
an object in a category
```

Softland:

```text
ObjectContainer
local world
model fragment
claim
experiment
paper/log
simulation
research program
```

Design:

```text
An object is whatever can be returned to, acted on, related, transformed, and
viewed at multiple scales.
```

### Morphism / Arrow

Math:

```text
a structure-respecting map from one object to another
```

Softland:

```text
explains
depends-on
derives-from
supports
contradicts
uses
translates-to
abstracts
specializes
simulates
refines
teaches
maps-into-my-model
```

Design:

```text
The arrow should be inspectable as a first-class thing, with type, direction,
source, confidence, cost, loss, and examples.
```

### Composition

Math:

```text
if A -> B and B -> C, then A -> C
```

Softland:

```text
paper claim -> model update -> simulation consequence
chat decision -> code change -> product behavior
concept prerequisite -> explanation -> learner understanding
```

Design:

```text
The system should let users follow composed paths and see whether the composed
meaning still holds.
```

### Commutative Diagram

Math:

```text
two paths from A to D agree
```

Softland:

```text
Does reading the paper then running the model lead to the same conclusion as
following the expert's explanation?

Does the code implementation match the design decision trail?

Does the metaphor used to teach the concept preserve the important structure?
```

Design:

```text
Disagreement can be shown as a non-commuting diagram.
```

This is huge. It means conflict is not a messy comment thread. Conflict is a
visible structural failure:

```text
path 1 says X
path 2 says Y
these should agree but do not
```

### Functor

Math:

```text
a map between categories preserving objects, arrows, identities, and
composition
```

Softland:

```text
zoom transformation
view projection
domain translation
teaching path
simulation abstraction
paper-to-model mapping
expert-world to learner-world translation
```

Design:

```text
A good zoom level is a functor.
It changes representation while preserving the structure that matters.
```

This connects directly to semantic zoom:

```text
60k-foot view -> 30k-foot view -> local world -> model REPL -> source bedrock
```

Each zoom transformation must preserve:

```text
identity
relation
confidence
time
agency
open questions
```

If zoom loses these, it is not semantic zoom. It is navigation between
unrelated screens.

### Natural Transformation

Math:

```text
a coherent transformation between functors
```

Softland:

```text
two different ways of explaining the same domain
two projections of the same local world
two models of the same phenomenon
two agents' interpretations of the same evidence
```

Design:

```text
The UI should show when two views are different but coherently related.
```

Example:

```text
outline explanation
  and
simulation view

are not identical, but they should correspond object-by-object and relation-by-
relation where they claim to represent the same thing.
```

### Adjunction

Math:

```text
a pair of translations between worlds with a best-approximation relationship
```

Softland:

```text
concrete example <-> abstract theory
detailed paper <-> compressed summary
simulation <-> equation
expert model <-> learner model
```

Design:

```text
Softland should make lossy translation explicit.
```

Not every compression is an equivalence. Some zoom-outs are approximations.
The UI should show:

```text
what was preserved
what was forgotten
what can be recovered
what is only an approximation
```

### Limit

Math:

```text
a universal way of satisfying many constraints at once
```

Softland:

```text
the common structure shared by several perspectives
the consensus interface between models
the stable shape all views agree on
```

Design:

```text
Consensus is not a vibe. It is the visible common structure preserved across
perspectives.
```

### Colimit / Pushout

Math:

```text
a universal way of gluing structures together
```

Softland:

```text
synthesis from disagreement
merging two local worlds
combining a paper's model with an existing field model
integrating code trail + chat trail + issue trail
```

Design:

```text
Synthesis should be shown as a constructed object with gluing points, unresolved
seams, and provenance.
```

Not:

```text
summary
```

But:

```text
this synthesis glues A and B along shared structure C,
preserves these differences,
and creates this new model D
```

### Pullback

Math:

```text
a shared context induced by two maps into a common target
```

Softland:

```text
two papers talk about the same dataset
two agents reason about the same source
two explanations use the same example
two theories constrain the same observation
```

Design:

```text
The UI should let users find the shared grounding where two views meet.
```

### Sheaf

Math:

```text
local data that can be consistently glued into global data when overlaps agree
```

Softland:

```text
local worlds as partial perspectives
overlaps as shared concepts/evidence/examples
global understanding as something that can only be glued when overlaps cohere
```

Design:

```text
Global knowledge should emerge from compatible local worlds, not from a forced
single map.
```

This is a better formal basis for "conflicts are good for progress."

Conflict means:

```text
local sections do not glue yet
```

Progress means:

```text
find the obstruction, refine the overlap, create a better gluing
```

### Lens

Math / applied category theory:

```text
bidirectional transformation between views or schemas
```

Softland:

```text
outline <-> canvas
raw source <-> native object
expert model <-> learner model
paper log <-> simulation
```

Design:

```text
Editing one view should say what changes in the underlying world and what does
not.
```

This matters later for malleability.

### Fibration / Indexed Category

Math:

```text
structures varying over contexts
```

Softland:

```text
the same object situated in different local worlds
the same claim under different assumptions
the same model at different zoom levels
```

Design:

```text
Context is not metadata. Context changes what operations and interpretations
are valid.
```

## The Big Softland Design Thesis

Softland is category theory for inhabitable understanding.

More precise:

```text
Softland is a world where information becomes composable local worlds, and
where the maps between worlds are visible, testable, replayable, and
transformable.
```

The product is not only about storing knowledge objects. It is about letting
humans and AIs build, compare, and compose maps between models.

## ZUI Through The Categorical Lens

ZUI is likely the right navigation grammar, but not because pan-and-zoom is
cool.

ZUI is right because knowledge has lawful changes of scale.

At each zoom level, the same underlying world is represented by a different
category of objects and arrows:

```text
Zoom 0.001 - Knowledge Earth
  fields, frontiers, schools, maturity, open questions

Zoom 0.01 - Domain Atlas
  subdomains, research programs, major models, datasets, labs

Zoom 0.1 - Topic / Debate Region
  claims, evidence, papers, methods, competing theories

Zoom 1.0 - Local World
  active model, discourse, simulation, trail, question, tools

Zoom 10.0 - Model / REPL Ground
  variables, mechanisms, executable examples, perturbations

Zoom 100.0 - Source / Bedrock
  code, data, raw logs, paper sections, provenance, event history
```

The zoom maps between these levels must be functorial:

```text
objects remain identifiable
arrows remain meaningful
composition remains legible
uncertainty remains visible
actions remain appropriate to the level
```

This is the design meaning of category theory here.

## Learning As A Functor

Learning is not "read content."

Learning is:

```text
construct a structure-preserving map from the source world into my current
world, then use that map to act.
```

The UI should make this visible.

For a learner entering autoimmune disease:

```text
field model
  -> beginner scaffold
  -> mechanism model
  -> evidence map
  -> simulation
  -> open problem
  -> contribution path
```

Each arrow should answer:

```text
what is being preserved?
what is being simplified?
what prerequisite is assumed?
what example grounds it?
what can I manipulate here?
what would count as understanding?
```

## Papers As Morphisms, Not Objects

In normal software:

```text
paper = document object
```

In Softland:

```text
paper = morphism from prior field model to updated field model
```

This is a major design correction.

A paper should answer:

```text
what world existed before this paper?
what transformation did the authors perform?
what experiment/model/path produced the change?
what field model changes if we accept it?
what remains uncertain?
what can be replayed?
what can be simulated?
what can be forked?
```

Therefore paper UI should not be:

```text
PDF + notes
```

It should be:

```text
before model
transformation trail
evidence path
simulation/model update
after model
open consequences
```

That is exactly the user's "paper should be a log" intuition, expressed
categorically.

## Conflict As Non-Commuting Diagram

Current collaboration tools treat conflict as:

```text
edit collision
merge problem
comment disagreement
```

Softland should treat conflict as:

```text
non-commuting diagram
```

Two paths should agree but do not:

```text
evidence -> theory -> prediction
evidence -> alternate theory -> prediction
```

or:

```text
design decision -> implementation -> behavior
design decision -> user's expectation -> behavior
```

If the endpoints differ, the disagreement is not noise. It is an object of
study.

Design consequence:

```text
Make disagreement navigable as structure.
```

The UI should show:

```text
paths that fail to commute
what each path assumes
where the divergence starts
what evidence could repair it
whether synthesis is possible
```

## Synthesis As Colimit, Not Summary

Summary says:

```text
Here are the main points.
```

Synthesis says:

```text
Here is the new object formed by gluing these perspectives along their shared
structure, preserving this disagreement, and resolving that tension.
```

Softland should design synthesis as an artifact with:

```text
inputs
shared overlap
gluing decisions
discarded assumptions
preserved conflicts
new claims
new affordances
provenance
```

This is much closer to collective intelligence than "summarize chat."

## Collective Intelligence As Model Alignment

The Topos-style framing suggests that collective intelligence is not:

```text
many people editing one document
```

It is:

```text
many partial models becoming composable without collapsing their differences too
early
```

Softland collaboration should therefore show:

```text
whose model is this?
which assumptions does it carry?
what does it align with?
where does it fail to align?
what translation makes collaboration possible?
what synthesis object emerged?
```

This is why "conflicts are good for progress" is not just a slogan. It is a
design requirement.

## Design Questions From The Category Theory POV

Ask these when designing a Softland view:

```text
1. What are the objects at this zoom level?

2. What are the arrows at this zoom level?

3. Which arrows compose?

4. Which paths should commute?

5. Which paths fail to commute, and is that visible?

6. What is the functor from this zoom level to the next?

7. What does that functor preserve?

8. What does it forget or approximate?

9. What is the local world's boundary/interface?

10. How can another local world compose with it?

11. Is disagreement represented as structure or flattened as comments?

12. What synthesis/gluing operation is possible?

13. What source/provenance remains recoverable?

14. What actions are valid in this context?

15. What would count as understanding here?
```

These are better design questions than:

```text
what panes should we show?
what graph layout should we use?
what color should relation edges be?
```

## Implications For The Next Import-Facing View

The import-facing Source-to-World view remains valid, but it should be framed
as the entrance to a larger categorical world.

Near-term view:

```text
raw source -> native object
```

Big-world continuity:

```text
native object -> local world -> model -> simulation -> synthesis -> contribution
```

So import UI should not overfit to provenance. It should also show the first
available arrows into future work:

```text
use in local world
compare to existing model
attach to claim/evidence
place in discourse graph
simulate if model-backed
start synthesis
ask for teaching path
```

## Implications For Knowledge Earth ZUI

The big ZUI must not only show levels. It must show functors between levels.

For every zoom transition, ask:

```text
what objects disappear?
what objects aggregate?
what arrows survive?
what uncertainty survives?
what actions become available or unavailable?
what examples ground the abstraction?
```

The UI should expose the zoom as lawful compression:

```text
field -> topic -> claim -> evidence -> model -> source
```

not as arbitrary navigation:

```text
page -> page -> page -> page
```
