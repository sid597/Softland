## Part 2 — derivations

- **Liveness follows composition, not packaging.** The compile pass gives the position of every binding's last read; what a binding holds at that position is a value, and a value may be a record or an array holding a surface. So the alive test at a position is "does any binding still to be read reach this surface", where reach walks arrays and plain objects and stops at a surface. Two properties make this sound on the bench: every aggregate the executor makes is a plain object or array (a definition's `emit` builds objects, `map` builds arrays), and a record root never holds a surface except directly (`surface.initial`), so the record's proxies are never walked and the unread-field list stays a list of what the construction read. The same walk serves the release at `next` (what the old state reached and the new does not) and the checkpoint's capture (what the state reaches, once per key). One definition, three uses, as the definer asked.
- **Why the cross-record binding is the executor's and the pack is the packer's.** A reference `{ result, output }` names a producer and one of its outputs; resolving it means running the producer (per its own edits) and reading the value it returned, which is what the executor does for every other binding. The consumer's pack (tolerance, placement) is per scale and belongs to the packer, as for any region. So the two rates separate by piece: the arrangement reruns when the network is edited; a camera move repacks the same returned path. The "producing revision" is the held record's identity plus the revision at which it ran; the "source correspondence" needs no new field, it rides on the returned path (each segment's edge and interval, the face's id and loop).
- **Why the wire carries the dependency key and not the record.** A load must answer "is this continuation still the continuation of this record", and the key already is that answer (the program's text, the record bindings the construction reads, the surface declaration, the read item fields for the items before the checkpoint, the capabilities). Carrying the key makes the definer's four edits decidable with `checkpointWhy` unchanged; carrying the record would make the load re-derive the key and also carry bindings the construction never read. The size, map and colour checks on each resource are a second line: the key already refuses a redeclared surface, and the resource checks refuse a wire that lies about its own payload.
- **Why the bytes route is a stronger receipt than the in-memory one.** The in-memory checkpoint hands the destination the host's own value; the bytes route hands it a JSON text and nothing else, so what comes back had to survive the encoding (component by component, little-endian), the base64, the parse, the checks and the upload. The GPU's "restored 0 of 65,536 against the saved bytes" says the float upload and read-back are exact; the CPU's says the codec is. The resumed numbers then repeat session 11's, which is what a continuation should do.
- **Why the release at a last read and at `next` was double.** A binding's last read releases the value it held; at `next`, the previous state's fields that the new state no longer reaches are released too; for `state.surface` both fire on the same object. The GPU host's `newest` check made the second a no-op, so no pixel was ever wrong, but a host that counted would have counted twice (the strict adapter did). The executor now frees a value once.

- **Why the capabilities string did not change.** It names the behaviour of `sample`, `mix`, `paint` and the arrangement, and none of that changed this session; the executor's liveness, the clip's binding and the codec are not operations a result depends on. So it still reads "bench 9, session 11", a checkpoint key from session 11 still matches, and a wire the definer produced against commit 550ce4e with the same format loads on this bench. Bumping it would have refused every earlier checkpoint for no reason.
