## 1 · The story in fifteen lines

Plain words; the engine's own names for things are in *italics* on first use and defined in §3.

1. A render engine has one job: take a description of what is on the page, turn it into pixels every time something changes, and say what is under the mouse.
2. Here the description is **one store**. Every visible thing is a *slot* — a small tree of boxes already laid out, with its text, images, lines and 3D rooms flattened into plain arrays — keyed by **what** it shows (its *address*) and **where** it appears (its *view-instance*).
3. Boxes sit in *containers*. A container is one six-number transform (move, scale, rotate). The transform is never baked into the boxes — it is **one row in one table on the GPU**, applied in the shader — so moving a container rewrites one row, not every box.
4. Text is special. The *shaper* takes a line of text, a font and a width and decides **once** where every glyph goes (real shaping, word-wrap only at spaces and tabs). Everything downstream reuses that answer; nobody else measures.
5. Everything drawn belongs to one of **ten *families*** — box, shadow, two kinds of text, clip, image, path, connector, chrome (selection furniture), 3D region. Each family is cut in two: a **pure half** that derives geometry from the store (it runs on the JVM in tests) and a **GPU half** that packs bytes and owns its shader.
6. The store's things become one ordered list — the *tape* — sorted by document-order **data carried on each row** (layer, pass, nesting path, rank), never by position in an array. Paint walks the tape forward; picking walks it backward, on the CPU, against box bounds.
7. Each frame opens with one question per family: **did any input you declared change since last frame?** Only the families that say yes re-produce their rows; the rows merge into a kept, sorted *arrangement*.
8. Change arrives as minted *deltas* — a row inserted or moved, a container changed, a region added, the viewport resized — minted by **whoever made the change**. Nothing scans the scene to discover what changed.
9. One small reducer folds the deltas into the *semantic state*: which containers carry an *effect* (opacity, mask, blur) over which row ranges, and the frame *plan* (which passes draw into which textures). Every maintained view has a from-scratch twin — its *oracle* — it can be checked against.
10. Then the GPU. **Every drawable is the same unit square, instanced.** Per-instance data (rectangle, color, corner radii, glyph uv, container row index) sits in a buffer; the vertex shader reads the container row and the camera and places the square; the fragment shader computes coverage — a rounded box by distance field, a shadow by a Gaussian, a glyph from an MSDF atlas or solved from its outline curves, an image by sampling.
11. Two roads out. The *legacy* road opens one pass straight onto the canvas and walks the tape. The *linear* road goes through the *compositor*: the scene into a 16-bit-float texture, each effect group into its own texture, blur / mask / composite, then one present pass that converts to sRGB. A target pool leases those textures and **refuses past a budget**; blur degrades instead of dying.
12. A *scheduler* decides whether a frame needs encoding at all — from causes (world, viewport, interaction, clock…) and registered deadlines — and time is **handed in as a value**, never read inside derivation.
13. A 3D region is a whole 3D scene that appears as **one row on the tape**: its own camera, meshes, lights, shadows and depth, rendered into its own leased texture, then drawn as a quad like anything else; a pointer into it is routed to a resolver that picks inside.
14. The *verifier* is a browser harness that builds the real systems, renders small cases twice, hashes the bytes against golden manifests, replays the scheduler, and runs source-level fences ("no family gets a private draw path", "nobody measures text privately").
15. What is alive today: **only the verifier drives any of it.** The one function that does a whole frame has no caller — the product client that used to call it was cut at the waist — so this is an engine on blocks, proven by its harness, waiting for a host.

Sentences 2–9 are the CPU side (all of it pure, JVM-testable, except the atoms in the runtime). 10–11 are the GPU side. 12–14 are the edges.

Three one-idea pictures (drawn in the HTML twin): *store → tape → frame plan → GPU → pixels, pick walks the same tape backward (CPU)* · *one unit square × N instances → vertex shader (rect · radii · color · uv + container row + camera) → fragment shader (coverage)* · *last inputs per family → changed? (declared keys only) → yes: re-produce rows / no: keep last rows; the sorted arrangement is kept between frames.*

## 2 · The shape every engine like this has → ours

General knowledge, not from the repo: the parts any retained-mode 2D canvas renderer ends up having (Figma's, tldraw's, Zed's GPUI, Flutter/Skia, Vello). Right column = where Softland keeps that part (names = the eight boxes of the kept-code map).

| any engine has… | what it does there | in Softland it is… |
|---|---|---|
| a retained scene (display list / scene graph) + a layout | the description of what's on screen, kept between frames; boxes nested in boxes; a layout pass | **Scene values** (the store · rect tree · containers · the tape) fed by the **Presentation grammar** (faces as data), owned at runtime by **Scene runtime** |
| a text engine (shaping + line breaking + glyph raster) | HarfBuzz-class shaping → positioned glyphs; a line breaker; glyphs rasterized into an atlas (bitmap/SDF) or solved from outlines | **The shaper** (HarfBuzz wasm + bidi · one shape per line · whitespace-only cuts · planes) → the renderer's two text systems (MSDF atlas · Slug outlines) |
| a damage / invalidation layer | knowing what changed so you don't redraw everything | **Frame computation** — inputs (per-family "did my declared inputs change?"), minted deltas, the one reducer, maintained views with oracles |
| a render plan (render graph / frame graph) | which passes draw into which textures, in what order; resources declared, validated, reused | the plan view + graph inside **Frame computation** (passes · resources · ten laws · export plan · structural reuse) |
| batching into GPU draws (materials / render features) | per kind of drawable: a pipeline, an instance layout, a packer, an executor | **Render families** (material half + GPU half per family) + the six systems inside the **WebGPU core** |
| a compositor | offscreen targets for effects: groups, blur, masks, color management, one present pass | the compositor inside the **WebGPU core** (rgba16float targets · leased from a refusing pool · linear → sRGB present) |
| hit-testing | CPU reverse walk, or a GPU id buffer | CPU: the tape walked in reverse against rect-tree bounds + per-family narrow predicates (**Scene values**); regions route to their own resolver |
| a frame loop / scheduler | draw only when dirty; animations register deadlines; time enters at the edge | the scheduler inside **Frame computation** (seven causes · deadlines · pure decide · replay) — present, tested, not wired to a running loop today |
| a test harness | golden images, determinism, replay | **The verifier** (render twice → hash vs manifest · replay byte-identical · static fences over the source) |

Two things are unusual about ours, both from settled law rather than engine habit: (a) the scene is **keyed values all the way down** — identity never position — because the store contract was mined from Electric's keyed-diff internals and re-keyed for the GPU (decisions.md "The render seam"); (b) **every incremental thing keeps its batch twin alive as an oracle** — the "fenced incremental view" — so the engine can be rebuilt piece by piece while staying checkable.

## 3 · The words this page uses

| word | meaning here |
|---|---|
| slot | one view-instance's whole render answer, precomputed: laid-out tree of boxes (container-local), flattened ops per family, address index. A map value keyed by view-instance. |
| address · view-instance | address = *what* is shown (a block's id); view-instance = *which appearance* of it. One address can appear in many slots. |
| container | a node in a transform hierarchy; one six-number affine `[a b c d tx ty]`; effective = parent ∘ local; carries a compact *transport slot* = its row index in the GPU table. |
| family | one kind of drawable. Ten: rect · shadow · msdf · slug · clip · image · path · connector · chrome · region-3d. Registered as data; no family gets a branch in the core walkers. |
| tape · entry · arrangement | the tape = the one ordered list of entries for a frame; entry = one row (id · family · order tokens · paint pointer · pick policy · visibility); arrangement = the tape as a kept sorted map, maintained by insert/remove between frames. |
| order tokens | the sort key on each row: stratum (world / overlay / region-composite) · pass class · nested stack path · part rank · stable tie. Document order is data, never array position. |
| delta | a minted change value: entry insert/move/remove · container (topology vs parameter) · region topology · global · region lease · region payload · viewport size. |
| effect · span · plan | effect = container-level compositing declaration (opacity · mask · layer blur · backdrop blur · isolate); span = entry ranges a container's effect covers; plan = passes + resources for this frame. |
| maintained view · oracle · fence | maintained = updated incrementally from deltas; oracle = the same answer recomputed from scratch; fence = the check that the two agree (a test, or a flag-on twin check at runtime). |
| material half · GPU half | a family's pure side (grammar, geometry, routing, tessellation — `.cljc`) vs its GPU side (pipeline, packed bytes, upload gate — `.cljs`). |
| road | a code path you can choose between: legacy vs linear (compositor); MSDF vs Slug for text; shaped vs legacy-monospace for layout. |
| receipt · golden · fence (.mjs) | receipt = a published measurement on `globalThis`; golden = a rendered case hashed against a manifest; fence = a static check over source text forbidding a class of regression. |
| PARKED · CUSTODY · LIVE | Sid's word for this area (guarded by the verifier build, no product entry) · kept only for TrailView / anatomy / goldens, one-cut deletion debt · has a runtime caller today. |

## 5 · The eight pieces, opened

Order = the flow: what describes the page → who owns it at runtime → text → the families → the frame layer → the GPU → the harness.

### A · Presentation grammar — CUSTODY

`workspace/face_assembly.cljc` 31K · `face_primitives.cljc` 62K

**What it is.** The thing that turns "a face" — a block's look, written as pure data — into a tree of boxes the scene store can lay out. A face is an *assembly*: nested maps of `{:prim … :props … :children …}`, `{:each … :template …}`, `{:bind [...]}`; no lists, no symbols, no logic — arrangement only. An *interpreter* walks it over a registry of 16 primitive builders and returns rect-tree nodes. Kept only because TrailView, anatomy and the goldens still wear it; one-cut deletion debt (Sid, 08-20).

**How it works here.** Two stages: `compile-assembly` once at wear time (closures over the registry), `apply-assembly` at data-change time (compiled + data + view context → rt-tree). Frame time does nothing new. Both are total — a malformed assembly, an unknown primitive, a throwing primitive all resolve to a renderable *error card* (assembly name, grammar version, address, first five errors), so a bad AI-authored face lands as a card beside the chat, never a black screen. Primitives measure their own bounds bottom-up ("measure in the primitive, arrange in the engine").

| sub-piece | what it is · how | in → out | why shaped so | talks to | state |
|---|---|---|---|---|---|
| assembly interpreter | the two-stage walk over a builder registry; the guard (no list/symbol); the error-card constructor is registry-independent | assembly EDN + data projection + view-ctx → an rt-node tree | "Furniture is data: faces/assemblies are arrangement-only data over a primitive vocabulary" (settled 07-11); interpretation cost on the data-change path, never the frame path | `scene_store/build-face-tree` (its one product caller) · the server's `assembly_adapter.clj` (the only server→client bridge) | CUSTODY |
| primitive vocabulary | 16 builders as a plain value: harvested `ui-*` builders, the trail-face omission cards, two new (`:text-run`, `:indent-rail`), the bare `:stack`; each `(fn [ctx props children] → rt-node)` | keyword + props + built children → an rt-node with measured bounds | persisted form is keyword + code-address, never fn values; pure `.cljc` so the goldens run on the JVM | rect_tree · text_layout (text-run measures through the shaper) | CUSTODY |

*In any engine* this is the UI description language (React elements, Flutter widgets) — except here it is data on purpose: an agent can author it, the server can store it, nothing in it can run.

### C · Scene values — PARKED

`workspace/scene_store.cljc` 35K · `rect_tree.cljc` 35K · `containers.cljc` 12K · `substrate/scene_tape.cljc` 33K · `selection.cljc` 6K · `snap.cljc` 11K — all pure `.cljc`, every one with JVM tests

**What it is.** The description of what is on screen, as a value. No atoms, no GPU, no browser. Four ideas: the **store** (what is shown, where), the **rect tree** (how a thing is laid out into boxes and flattened into per-family arrays), **containers** (the transform hierarchy), the **tape** (the one ordered list a frame draws from and picks from).

**How it works here.** A slot is one view-instance's whole render answer, computed once at upsert: its resolved tree (container-local coordinates), eight flat op arrays (text · rects · shadows · images · regions · paths · connectors · chromes) with the container index baked in, and its `address → index-paths` map. The store keeps `{:slots :index :ordered}`: slots by view-instance, an address→view-instances index maintained incrementally, a sorted map of tape entries. Nothing recomputes them by scanning at read time. Picking: bounds broad phase, children front-to-back, a per-family narrow predicate (path, connector, chrome bring real math; the rest say yes), then the hit path bubbled leaf-first.

### B · Scene runtime — PARKED

`workspace/scene_runtime.cljs` 30K · `chrome_runtime.cljs` 17K · `region3d_runtime.cljs` 28K · `frame_runtime.cljs` 15K — `.cljs`, no JVM tests, zero callers except among themselves (and two receipt fns from the verifier)

**What it is.** The owner of the atoms: one store atom, one container-registry atom, a journal of container deltas, face lifecycle, the last pick, the action registry, three Missionary views the (now deleted) product loop sampled. The chrome and region3d runtimes are the same idea for their own session truth; the frame runtime is the W4 fixture join.

**How it works here.** Mutations only at edges (a window API, the server echo fan-out) — never inside a reactive derivation. Every container mutation mints a delta from before/after and appends it to a journal with a sequence number; consumers read a snapshot and ack a high-water mark. Face instances get a container id from a recycling pool (a monotonic counter walked into the GPU table's ceiling after ~992 spawn/despawn cycles and killed the reactor — F3, 07-13), the container is added first, then the slot. The three views: `<store-frame` (one `m/latest` over the store → the GPU payload), `<effective`, `<frame-registry`. The file still names `render.cljs`, `mouse.cljs`, `face_wiring`, `agent_flow` — none exist any more.

### D · The shaper — PARKED-but-floor

`workspace/text_layout.cljc` 73K · `text_layout_planes.cljc` 25K · `text_shaper.cljs` 14K · `runtime/fonts.cljs` 13K — text-layout tests + shaping-correction test + two static fences green

**What it is.** Text in, placement out. One entry, `layout`, takes text + font + size + line height + width (or a wrap column) + a layout key and returns one immutable, versioned value: lines (baseline, advance, logical and ink bounds, glyphs with id · position · advance · cluster → source range, clusters, runs), metrics, a clip plan, receipts. Seven readers (measure · wrap · paint · caret · selection · clip · hit-test) echo its id. Nobody else measures — a fence forbids private metric arithmetic anywhere in `src/app`.

**How it works here.** For each source line the provider shapes the *whole line once* (HarfBuzz wasm, bidi); the layout walks clusters accumulating advance until the width is exceeded, remembering the last whitespace run — that run is the cut. Only SPACE and TAB break (never `\s`, so NBSP never breaks); if nothing fits, a hard cut at one cluster (an emoji stays whole). Whitespace is consumed (owned, painted as nothing) so copy returns it and the caret can sit in it. Widths are HarfBuzz advances in font units — never `measureText`. A wrap column becomes a width by shaping one space and multiplying. The pure layout never measures: the provider is injected, so JVM tests use a synthetic one. Results are compacted into *planes* (typed arrays); glyph/cluster maps are rebuilt at the accessor boundary — retaining them cost ~150 MB on a 228k-glyph boot (2026-08-08).

### E · Frame computation — PARKED

`substrate/frame_inputs` 9K · `frame_delta` 8K · `frame_semantic_state` 3K · `frame_effects` 14K · `frame_effect_view` 12K · `frame_graph` 42K · `frame_plan_view` 16K · `frame_scheduler` 8K — all pure `.cljc`, every one with JVM tests; the only production caller is the frame function

**What it is.** The render-seam law as code: the layer between "what is on screen" and "how the GPU draws it" that decides *what changed*, *what that changes*, *what passes to run* — and keeps every incremental answer checkable against a from-scratch one. Also the scheduler.

**How it works here — one frame, in order.** (1) The frame function gathers this frame's raw values and asks `changed-families`: compare to last frame, key by key, per family's declared inputs → only the stale families. (2) Only those families' producers run; entries fold into the kept sorted arrangement; old-vs-new keys become entry deltas (insert · move · remove). (3) Container deltas drained from the runtime's journal, region-topology deltas from the region bindings, global and viewport deltas minted inline. (4) All *semantic* deltas into one call — `apply-deltas`, a 65-line reducer — which runs the effect view then the plan view and returns state + work counters; an empty delta set returns the *identical* prior state. Binding deltas (region lease · region payload · viewport size) bypass the reducer. (5) Out: effect spans and the plan; the compositor takes both. (6) Behind a flag, the twin check recomputes each maintained view with its oracle and asserts equality. The ledger counts every comparator call, upsert, fragment touched and publishes to `globalThis`.

**What it is.** The part that speaks WebGPU: builds the pipelines, owns the buffers and textures, turns tape entries into draw calls, encodes a frame. **How it works here.** No vertex buffers of geometry: every pipeline draws `(6, N)` — six corners of a unit square from `vertex_index`, N instances — and the one vertex-buffer slot carries per-instance data. ## 6 · How it came to be this shape — the waves

"Why is it implemented this way?" has two answers. The settled laws (one render substrate · the render seam · the spatial model · furniture is data) are the *intended* shape. The *actual* shape also carries the order things arrived in — five waves in nine months, each under its own contract, each adding a layer and keeping the previous one alive as oracle or fallback. Hence three `apply-deltas`, two text roads, two render roads, a maintained plan and a batch plan, a duplicated `legal-causes`.
