## The position

What we have is one layer built three times in its middle and zero times at its floor and its edges. The middle is the thing both repetition readers found: a tool applied to a subject, placed, with what it reads declared and its last full input kept, so the loop knows when to rerun it and a hit knows what it landed on. Claude's read named it the mount, Codex's the representation instance. Each build wrote it privately, three field lists, three loops walking it. The floor is the record shape the mount is written in, and the executor's suspension model under that. The edges are the owners: host, wire, store, effects. No build shares a floor or an edge with another, and the two builds in one tree diverged on the wire.

What should exist before the next build, in this order:

1. **One tree.** Three trees hold three executors and two Region3D forks. The docs cannot size the merge. It closes by one diff and it comes before anything else.
2. **One envelope, one wire.** Workspace's envelope, plus Place's declared inputs by record and path, plus Vantage's selector for which revision an address resolves to. Vantage's repaired edit path as the wire, since it carries kind and visibility, the graduation-id fix and layer metadata. Workspace's bypass retires or is shown to be that same path. This is a choice and a deletion, not a build.
3. **One read: what a program step can say.** Every program shown is arithmetic and field access. Nobody states more. The answer decides whether the mount's tool field can hold a projection or only a brush.
4. **The build: the mount as one record kind on that envelope, and the rerun rule once, with levels.** The three clients become three vantages over it. That is the next test of the hypothesis: not a fourth client, three existing ones re-hosted. If re-hosting three costs less than the smallest of them cost to build, the layer exists.

Not first: kinds as records, the placement language, a generic scheduler, another client. Reasons sit in the sections below.

One correction to Claude's repetition read that changes the mount's field list. It says the last full input does three jobs: rerun key, read-reuse key, hit ground. So a mount holds its last full input and its pending requests, each with its own identity. The store holds derivation key to result. Not one field.

`★ Insight ─────────────────────────────────────`
Two mounts can ask the same read with the same full arguments and must share one stored answer, which is what a derivation key is for. But only the mount that asked may consume it against the snapshot it drew, which is what the request identity is for. Collapsing them onto one field would let a stale mount accept a fresh answer or make two mounts recompute what one already has. Workspace built the first half, W:82; Vantage built the second, V:163; the mount needs both slots, not one.
