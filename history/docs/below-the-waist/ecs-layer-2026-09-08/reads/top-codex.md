That is the missing layer I would pursue. The three builds give us substantial pieces of it. They also give us a fairly precise account of the application code it must replace.

The baseline already supplies recipes, execution, continuations, rendering, individual locators, editing geometry and durable revision machinery. The builds supplied the connections around them. Place connects ongoing input to addressed tool inputs, computation, pixels and another edit. Workspace makes subjects, tools and retained investigations independently addressable and durable. **The “mounted tool” found by repetition accounts for the center of the gaps list. It gives those nouns a relationship; it does not supply all their semantics.** “This material, through this tool, here” explains why record identity, computation, pointing, editing and working context repeatedly arrived together. I would organize the common code around that relationship:

| What the gaps pair named | What the shared layer should provide |
|---|---|
| Client records and reference rules | A tool instance identifies its subject and tool definition separately, with explicit rules for resolving their references. |
| Change delivery, reruns and input levels | Its computations declare the values they consume. The host delivers changes, compares those values, and runs or resumes the affected computation. |
| Subject/tool/view composition | An executable description selects inputs, constructs views and arranges instances. The host can admit another instance from that description. |
| Rendered hits and source inspection | Meaningful output parts retain subject/tool addresses and the view state against which those addresses were obtained. |
| Record editing and tool-field editing | An action binding names the target, value conversion, commit policy and write destination; shared machinery carries out the edit. |
| Working context | Saved context retains the instances, their arrangement, their reference choices and the material held beside them. |

The browser host owns the lifetime of these things: input, outstanding work, presentation and resources. That is a coherent layer around one central unit. It still has several responsibilities that need actual implementations. The repetition referee is right to preserve the gap between finding that unit and claiming that one combined loop follows automatically. [Repetition comparison](</mnt/data/projects/Softland/docs/below-the-waist/ecs-layer-2026-09-08/reads/merge-repetition.md:14>).

The remaining gaps belong at different places around it. The painted-surface connection and executable text belong to the capability vocabulary. Durable acceptance, authoring layers and read-work custody supply services the tool instance uses. A readable prompt can be another tool, while invoking an agent retains its process owner. Traces, imported code and construction explanations become material for tools to show; producing their evidence remains separate work. In particular, imported source does not supply the authored explanation that would make Inside or Anatomy dispensable.

There is one consequential limit to the proposed unification: **complete inputs are a shared principle, but the rerun input, a reusable read’s arguments and a pointer’s validity snapshot are different values serving different purposes.** Keeping one “last input” on a mount does not automatically establish all three. The baseline already distinguishes shared read identity from the request that determines whether a particular suspended consumer may accept an answer. **The boundary pair adds a criterion for the next build more than it adds facts about the existing builds.** The write-ups already say that composition, projection, interaction and tool admission remain substantially compiled. They already distinguish fields that exist from behavior that consumes them. The useful further step is to ask *which decision actually moved*.

A program that calls “build this inspector” can leave its field choices, arrangement and actions inside that capability. For those decisions to become authorable, the program needs operations at the level of selecting fields, following references, constructing addressed rows, arranging views and specifying actions. That is the boundary pair’s strongest contribution: it makes “more behavior as records” assessable. A callable application function does not become a reusable foundation merely because a record invokes it. [Boundary comparison](</mnt/data/projects/Softland/docs/below-the-waist/ecs-layer-2026-09-08/reads/merge-boundary.md:51>).

The pair does **not** establish that the existing executor can express all of this, that an added set of capabilities will necessarily suffice, or that the host will reduce to four owners with no remaining tool-specific code. Those are proposed outcomes. The first implementation should settle the needed vocabulary against a real tool.

For the shared code, I would make these choices now:

- **References distinguish holding from following.** An exact revision reference keeps that revision even when the selected authoring layers change. A following reference resolves through its stated read context. Subject and tool references make those choices independently. An edit separately names its write destination and expected source state.
- **Composition and addressed actions are executable parts of the definition.** A placement label alone is insufficient. Code must consume the description of what appears together and what an action on a displayed part means.
- **Runtime state has an explicit owner.** Saved definitions and working context are distinct from previous inputs, derived layouts, continuations and device resources. A result becomes durable material when something deliberately retains it.
- **Correspondence is supplied and carried explicitly.** The layer can preserve an address, check a stale gesture and represent unresolved correspondence. A subject-specific tool must supply the mapping that says what a displayed part means. Exact references alone cannot decide whether an explanation still applies after a function splits or a subject is reinterpreted.

That requires a common meaning for addresses and actions. It does not require reconciling every record envelope, kind vocabulary and client wire before making progress.

**The first build should make one new inspector through this path, using Vantage’s existing durable editing facilities.** Its M1–M5 account already provides editable tool programs, saved revisions, selected layers, change delivery and a tool displaying its own record. Those are the strongest starting conditions for the missing test. The new work should extend that path beyond its fixed catalog and assembly. [Vantage’s tool-editing path](</mnt/data/projects/Softland-ecs-workspace-20260908/docs/below-the-waist/vantage/ROUND-ACCOUNT.md:162>).

Concretely, create an inspector definition from inside the client. Its program selects fields from a subject, follows one reference, constructs source-addressed rows and arranges them. One row offers an edit whose destination is part of the definition. Mount the inspector beside the original view, then use it on a passage and on the Text tool’s own record. Revise the inspector while retaining an instance of its earlier definition. Save and reload that working context.

The decisive change is that adding a field, a reference-following action or another instance changes records. The host has no new dispatch case for that inspector. This goes beyond the current numeric controls, list/columns choice and editable roots: it makes some of the surrounding interface constructible. It also exercises reference resolution, computation, composition, correspondence, editing and continuity together, so the common layer is developed against the connection all three builds needed.

The silences should be routed according to whether they ask about something already implemented or about a rule this new connection must have.

The inspector build should establish those rules in working code.
