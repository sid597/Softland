I’ll use the four documents as the ground, compare what each build put into records and left in code, then work through the common remainder. Where a writeup leaves the boundary or its reason unstated, I’ll flag that as a finding.


The baseline already had executable tool recipes, so “tools became data” would overstate what these builds added. Place/Inside moved the interactive working state into records, while leaving rules such as identity-to-inspector-text and architecture-to-mesh in code. I’m tracing that distinction through the other two: recording a rule’s inputs or output is different from recording the rule itself.


The other two accounts sharpen the same boundary. Workspace records can select a relation and list-or-columns presentation; Vantage records can carry complete programs and authored rules. Yet both still need application code to compose the surrounding interface and connect gestures to actions. That looks like the substantive common remainder, separate from the renderer, interpreter and process owners that execute it.


The reports describe two reasons code stayed: some supplies operations and owns live resources; some encodes choices made for that particular prototype. The second group includes which fields an inspector shows, how views compose, and what a gesture does. None of the reports establishes that those choices cannot move into records. They leave open the vocabulary and execution support needed to move them.


**Across all three, the recurring remainder is the code that turns records into an interactive application:** which things appear together, how they are transformed into views, what pointing means, what an interaction changes, and how a new tool enters the running client.

There is also a foundation that stays in code: the interpreter, computational capabilities, rendering, storage mechanisms and resource ownership. Those two remainders have different explanations. The foundation supplies operations that records can invoke. The application code contains choices that these builds have only partly made expressible through records.

The documents support identifying that second remainder as the missing layer exposed by the experiments. They do **not** establish that it is intrinsically unable to move.

The baseline matters here. Executable recipes already existed: the pickup brush already described reading coating, mixing colour, constructing a footprint and painting; Path records already contained construction and width expressions. The builds extended the reach of that arrangement into ongoing input, inspection, editing, working context and, in two builds, durability. They did not originate the distinction between a tool program and its compiled capabilities. [Baseline]( /mnt/data/projects/Softland-ecs-layer/docs/below-the-waist/ecs-layer-2026-09-08/BASELINE.md:25)

**Place / Inside moved the live working situation into records.** That includes events and stroke points; paintings and retained source identities; pointer identity and stable inspection; traces; active tool inputs and outputs; vantage cameras, placements and navigation ancestry; and the numeric editor’s source address, buffer, caret and selection. Inside’s architecture nodes, descriptions, source addresses, positions and links are also records.

Behaviour is partly recorded too: brush recipes and parameters, the flow width expression, and a text program. Editing radius or the flow coefficient changes an actual consumed definition. These are in-memory records seeded from source; their being records is real, while independent durable authoring remains unfinished. [Place’s records/code boundary](/mnt/data/projects/Softland-ecs-layer/docs/below-the-waist/ecs-layer-2026-09-08/ECS-LAYER-WRITEUP.md:163)

What stayed in code was the construction of the application around them:

- Turning browser input into changes and dispatching the supported brush, inspector, flow and Inside behaviours.
- Joining a hit to its meaningful record/source identity.
- Turning identity into inspector lines, and traces into text and Path samples.
- Choosing editable fields and interpreting numeric edits.
- Interpreting navigation and gestures.
- Turning the architecture catalog into meshes, routes, headings and inspector content.

The new foundation work—holding a continuation at exhausted input, sphere-skin computation and GPU upload, for example—also remained code.

The stated reasons differ. Some foundation capabilities needed extension to support the live use. The numeric editor and Inside presentation were deliberately bounded implementations. For the application rules, the account explicitly says that moving them into tool records would require **vocabulary and execution support**. It does not demonstrate that those rules must remain code. [Implementation reasons](/mnt/data/projects/Softland-ecs-layer/docs/below-the-waist/ecs-layer-2026-09-08/ECS-LAYER-WRITEUP.md:225), [remaining boundary](/mnt/data/projects/Softland-ecs-layer/docs/below-the-waist/ecs-layer-2026-09-08/ECS-LAYER-WRITEUP.md:339)

**ECS Workspace moved an investigation and a small inspection definition into durable records.** Subjects, brush inputs, runs, observations, paintings, source passages and notes have identities and revisions. Relations hold exact references. A representation separately names its subject, tool, view and placement. The surrounding context retains baseline/candidate references, kept material, selected tools and saved view state. Pending reads have durable request/result identities.

Its clearest behavioural move is the inspection tool: the record chooses which relation to follow and whether to arrange the result as a list or columns. That definition can be revised, reused across runs and replaced by the pinned original.

What stayed in code was the meaning and composition surrounding those choices: the relation interpreter, the available arrangement semantics, control templates, drawing functions, panel dimensions, responsive layout, commands and navigation. The brush adapter and coating-to-mesh adapter also remained code. Anatomy’s chapters, explanation, visual construction and reveal rules were application-authored. Draft/IME state and some exploratory view state remained transient rather than becoming durable revisions. [Workspace’s boundary table](/mnt/data/projects/Softland-ecs-workspace-20260908/docs/ecs-workspace/SESSION-HANDOFF.md:62)

Here the reason is particularly explicit: **compiled templates made a complete first interface possible**. The build selected a small behavioural vocabulary to demonstrate saved variation and continuity. The baseline executor did not supply navigation, editing, persistence delivery or window lifetime, so the workspace connected those responsibilities in application code.

A saved placement such as “companion” therefore does not contain the layout that interprets it; a saved inspection definition does not contain the entire interaction through which it is used. The handoff calls those templates its largest remaining tool-authoring boundary. It also explicitly says the omitted capabilities were not shown impossible on the substrate. [Division rationale](/mnt/data/projects/Softland-ecs-workspace-20260908/docs/ecs-workspace/SESSION-HANDOFF.md:88), [what remains open](/mnt/data/projects/Softland-ecs-workspace-20260908/docs/ecs-workspace/SESSION-HANDOFF.md:123)

**Vantage moved tool definitions into the same durable editing and layering path as their subject matter.** Records carry the vantage’s subject/query, tools, pins, zoom, selected layers and parent; source material and candidate revisions; and Text, Map and Sphere roots and programs. Text font, wrapping and reading rules are values. The roots panel can address and edit complete programs through the ordinary source editor.

Agent work adds another behavioural example: prompt composition is a program over recorded inputs, and the turn records model, effort and rendered prompt. Reply attachment and generated reply kind have actual consumers of their recorded rules. Layer selection and promotion let a passage and the tool showing it travel through the same change path. [Vantage’s tool definition](/mnt/data/projects/Softland-ecs-workspace-20260908/docs/below-the-waist/vantage/ROUND-ACCOUNT.md:50), [prompt and tool editing](/mnt/data/projects/Softland-ecs-workspace-20260908/docs/below-the-waist/vantage/ROUND-ACCOUNT.md:130)

What stayed in code includes:

- The fixed conversation/map/roots page assembly and tool discovery, creation and mounting.
- Keyboard routing, dialogs, input handling and region-to-query gestures.
- The available capability and kind vocabulary.
- Application-specific computation inside capabilities—for example, the architecture map’s grouping interpretation, although its dimensions, spacing and colours are roots.
- Shared storage rules and the owners of delivery, processes, fonts, devices and GPU work.

The document’s reason for keeping capability implementations and effect owners explicit is clear. Its reason for the fixed shell is more limited: general composition and mounting were not implemented. It does not establish that the shell needs to remain compiled.

Vantage also supplies two useful checks on what “moved” means. A `:paste-share` field exists without a clipboard/share operation consuming it. Imported code is editable stored material, but editing that material does not update Git, compile it or change the running client. A field or a stored source program does not, by its presence alone, acquire operational meaning. [Vantage’s explicit boundary](/mnt/data/projects/Softland-ecs-workspace-20260908/docs/below-the-waist/vantage/ROUND-ACCOUNT.md:256), [map and stored-code limits](/mnt/data/projects/Softland-ecs-workspace-20260908/docs/below-the-waist/vantage/ROUND-ACCOUNT.md:197)

Across the three, I would identify the **application-specific code that repeatedly stayed behind** this way:

| Recurring code | Its forms in the builds | What would have to become expressible in records |
|---|---|---|
| **Projection and composition** | Identity-to-inspector-lines; fixed cards and Flow templates; architecture assembly; Vantage page assembly and map grouping | Which values to read, how to transform them, which representations to construct, and how to arrange those representations together |
| **Interaction and transitions** | Numeric editing rules; workspace commands and navigation; keyboard routing, dialogs and map gestures | Which addressed input or event triggers which condition, state change, navigation or edit |
| **Correspondence and edit destinations** | Pixel-to-source joins; recipe-step/spatial correspondence; region-to-query and source-field addressing | How a displayed part retains its subject/source address, and how an action on that part reaches the intended material |
| **Admitting and using tools** | Specific client dispatch; supported inspection choices; fixed tool catalog and mounting | How a tool declares its inputs, outputs, placement and interactions sufficiently for the client to use it without another application-specific dispatch case |

These are connected responsibilities. A card definition that controls appearance but cannot specify what its fields refer to or what editing them does leaves much of the card in code. An interaction definition that can issue an action but cannot be mounted in a view leaves its use in code.

**What would it take to move that remainder? My inference is: an executable vocabulary for composing the application, extending the record-program approach already present.** The documents do not imply that another entity envelope would accomplish it. Identity, references, revisions and tool records already exist in useful forms.

Concretely, consider Place’s inspector. Its record would need to express which fields to select, how to turn them into source-addressed rows, how to compose those rows, and what change an accepted edit emits. Text shaping can remain a capability. Applying a change can remain an owned operation. The decisions about *this inspector* would become its program.

Merely adding a capability called “build the current inspector” would move the invocation into a record while retaining those decisions inside the capability. To move the decisions, the operations exposed to the program must be reusable at a finer level: selecting fields, following references, formatting rows, composing views and expressing addressed actions. The same reasoning applies to Workspace’s cards and Vantage’s surrounding shell.

The existing recipe language should carry whatever composition it can already express. Where it cannot, it needs additional operations or execution support. **The four documents do not tell us precisely where that language limit lies.** They identify compiled rules and missing authoring support, but do not establish whether exposing more capabilities is sufficient or whether the executor’s composition/control model also needs extension. Nor do they derive a common minimum vocabulary across the three. Those are findings left open by the writeups.

The foundation has a different answer. Shaping, geometry, sampling and rendering supply computational meaning; the interpreter supplies program meaning; event loops, GPU resources and external processes require execution and lifetime ownership. Storage mechanisms supply identity and accepted-change rules. Records can describe requests, configurations and policies for these mechanisms, as the builds already demonstrate. Moving their implementation algorithms into records would require those algorithms to become executable content for an interpreter or compiler. None of these experiments attempts that further move, and some execution machinery would still carry it out.

The hypothesis therefore has a specific unfinished test: **can the composition and interaction choices now written as application code become programs over a reusable foundation?** These builds show several local successes—brush recipes, inspection variation, text and prompt programs—and repeatedly stop at the surrounding application. The meaningful further movement would be a new composition or interaction that can be defined, mounted and revised through records, with the existing capabilities executing it. That would address the code all three left behind.
