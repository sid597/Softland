  ★ Insight ─────────────────────────────────────
  Why <combined-text-ops stays in loop.cljs: This function is the biggest single
   m/latest in the codebase (~400 lines, 22+ args). It's the central join point
  where ALL text from ALL panels gets composed into one GPU buffer. It's
  inherently orchestration — it's WHERE the separate worlds (editor, chat,
  sidebar, cmd panel, settings) meet. Extracting it would just move the
  coupling, not eliminate it.

  Why the order matters: Leaf-first extraction means each step can be verified
  independently. events.cljs depends on nothing. layout.cljs depends on nothing
  internal. ui.cljs depends on layout. Each subsequent module depends only on
  already-extracted modules. If any step breaks, you know exactly what caused
  it.

  The Missionary climate effect: The m/join vector in start-loop! is where all
  flows converge. This is an inherent property of Missionary's architecture —
  reactive flow composition gravitates toward a single orchestration point. The
  refactor doesn't fight this. It accepts that loop.cljs will always be the
  conductor. But right now the conductor is also playing 12 instruments. After
  the refactor, it just conducts.

  The Hard Decisions (Scoped, Not Deferred)

  H1: submit-agent-run! (~470 lines) — stays in loop.cljs

  This is the giant case statement that handles ALL commands (:run,

  :flow-select, :flow-arrange, :flow-run, :flow-review, :flow-rework,
  :flow-finalize, :flow-status, :flow-reset).

  Why it stays: It directly mutates 10+ atoms (!flow-state, !agent-output,
  !scroll-y, !agent-scroll-y, !extract-preview, !ai-provider...). These atoms
  are created in start-loop!. Extracting submit-agent-run! would require passing
   all atoms as arguments — possible but the function signature becomes 15+
  args.

  Future refactor (not now): Split into submit-agent-command! (the :run case)
  and submit-flow-command! (all :flow-* cases). The flow commands would move to
  dg_flow.cljs as a closure that captures the atoms. But this is a second-pass
  concern.

  H2: Mouse consumer (~370 lines) — stays in loop.cljs

  The mousedown handler dispatches to settings panel, sidebar tree, status bar,
  command panel, flow canvas rect tree, file layout rect tree, and normal
  editor. It's the central input router.

  Why it stays: It reads !settings, !sidebar-state, !flow-state, !current-file,
  !viewport, !scroll-y, !drag-state, !editor-doc, !cmd-panel, !focus,
  !caret-visible, !trail-collapsed, !active-pane. That's 14 atoms via deref.
  This IS orchestration — routing input to the right subsystem.

  H3: Event routing fns (<editor-keys, etc.) — stays in loop.cljs

  5 functions, each 5–8 lines. They're m/eduction filters using @!focus. They
  could move to events.cljs but they conceptually belong at the orchestration
  level (they decide WHERE events go based on global focus state).

  H4: The :hardcode "button" case (~150 lines of inline rt-node) — stays for now

  The case "button" branch inside submit-agent-run! has ~150 lines of inline
  shadcn button demo nodes. This is JIT prototype code. It should eventually
  move to workflows/jit.cljs. But since the JIT workflow is stage 2 (embryonic)
  and this code is inside the command dispatch case, extracting it now would
  mean threading atoms through jit.cljs for one function. Not worth it yet. When
   JIT matures to stage 3, this naturally moves.

  ★ Insight ─────────────────────────────────────
  Three key architectural observations from reading every line:

  1. The atom threading pattern is what makes this possible. Every <flow
  function takes atoms as arguments rather than closing over them. This means
  extraction is mechanical — move the function, keep the signature, pass the
  same atoms from start-loop!. No state ownership changes.
  2. The real coupling is in the mouse consumer and submit-agent-run!. These are
   the two functions that read 10+ atoms and dispatch to multiple subsystems.
  They're genuinely orchestration — the conductor telling instruments when to
  play. Trying to extract them would just move the coupling, not eliminate it.
  3. <combined-text-ops is extractable because its coupling is explicit. All 28
  arguments are in the function signature. There's no hidden state. Moving it to
   its own file makes the join point visible ("this is where all text meets")
  without changing any behavior.
