Phase 7, the second number: lock store growth under hand layers
================================================================

Sid's phase 7 text (SPEC.md): "lock store growth under hand layers, bytes per
value and the curve over a hundred thousand values".

Run 25 September 2026, 11:46:38 to 12:03:57 IST (the numbers below); a first
full run 11:12 to 11:42 gave the same logical and key-value bytes and is
superseded for the compacted measure (see "Runs"). Machine: AMD Ryzen 9 9900X
(12 cores, 24 threads), 62 GB RAM, Linux 7.0.0-31-generic, OpenJDK 21.0.12.1.
Rama 1.6.0, in-process cluster, 1 task, 1 thread, 1 worker (replication
factor 1). Bytes only: nothing here is a timing.

What was built
--------------
A bench slice, not stage 2: src/rig/bench/lock_slice.clj, module
rig.bench.LockSlice. It follows PLAN-locks-and-forgetting.md, which is not
yet validated. Per value, one stream event on the layer's home task:
- a fresh 32-byte lock K (SecureRandom);
- the value's canonical EDN sealed under K with AES-256-GCM (12-byte nonce
  prepended, 16-byte tag), into the value's log row
  {:e :k :v <sealed> :replaces nil :mark #{} :lock-id [:value [name 0]] :lock nil}
  at [layer :log name];
- K wrapped under the person locks of the model's wrap under :owner-required
  (a hand layer: the owner required; others only when the value is marked
  :die-with-any), a chain of GCM seals in sorted order, as the lock record
  {:required [..] :any-of [] :blob <wrapped K> :any-blobs nil}, written as
  the lock row at [layer :locks [:value [name 0]]].
Person locks are fixed bench keys standing in for $$persons. The slice writes
nothing else: no answer record, :by-stamp, :heads, settings or stamps. Two
PStates of one schema: $$layers keeps ciphertext and wrapped locks as base64
text in String slots (the plan's L4); $$layers-raw keeps the same bytes raw
in byte/1 slots (Rama accepts byte/1 as a schema class).

Method
------
test/rig/bench/lock_bench.clj, from the rig folder:
    clojure -M:bench rig.bench.lock-bench run <variant,...|all> [values] [every]
    clojure -M:bench rig.bench.lock-bench report
Each variant: a fresh in-process cluster, 100,000 values into the hand layer
:alice-hand (owner :alice), one value per act, 64 appends in flight with full
ack, the same seeded values in every variant. Every 10,000 values the appends
are drained and four measures taken:
- logical: every lock row read back from [layer :locks] in pages, each sized
  in Rama 1.6.0's own serializers (key: rpl.rama.api.durable.rocksdb.
  key-encoding/k-ser; record: rpl.rama.util.nippy-serialization/freeze);
- raw KV: the key and value bytes of every RocksDB entry of the PState (both
  column families: Rama keeps top-level entries in "default" and every
  subindexed element in "subindexed");
- live dir: the file bytes of the PState's RocksDB directory in the
  cluster's temp dir, as it stands (WAL, SST, manifest, options; RocksDB's
  info LOG excluded; apparent length, not the WAL's preallocated blocks);
- compacted: that directory copied, opened with the options Rama wrote into
  it, flushed (recorded as "flushed SST"), then compacted with
  BottommostLevelCompaction kForce, so every point is a full rewrite (the
  settled size, with sequence numbers zeroed).
The lock store's own cost is the lock variant minus the no-lock variant (same
values, same log rows, no lock rows), point by point. Checks per variant: 100
sampled values read back; the slot is not the plaintext; each opens through
its lock row and the person locks; none opens without the owner's lock; in
the two-person variant none opens without Bob's; the no-lock variants have no
lock row.

-------------

           key :mention, marked :die-with-any                      (chain of two seals)
Each with and without lock rows: ten runs.

Reading the numbers
-------------------
Bytes per value of the lock store, at 100,000 values:
                        logical   raw KV   compacted disk   value rows, compacted
  40 B, base64 (L4)       189.0    192.2        107.9            156.3
  40 B, raw bytes         169.0    172.2         86.9            130.5
  200 B, base64           189.0    192.2        107.9            391.9
  200 B, raw bytes        169.0    172.2         86.9            305.0
  40 B, two people        233.0    236.2        148.0            157.8

- The cost per value is a constant: it does not depend on the value's size
  (189 B logical and 107.9 B on disk for both sizes). A base64 lock row is
  the lock id as key, 59 B, plus the record, 130 B: the wrapped lock 82 B
  (60 raw bytes = 12 nonce + 32 lock + 16 tag, as 80 base64 characters), the
  wrap list and map framing 48 B, of which the nil :any-blobs is 12 B and the
  empty :any-of 9 B.
- Raw bytes save 20 B logical (11%) and 21 B on disk (19%); Snappy does not
  win back base64's inflation on random bytes.
- Each extra required person (the chain form, a marked value) adds 44 B
  logical in base64 (32 to 35 raw) and 40 B on disk. In the copy form (any
  one of the people, shared layers; computed, not run) each person adds 91 to
  96 B in base64, 71 to 76 raw. An unmarked value about two people in a hand
  layer is wrapped under the owner alone (the model's :owner-required), so it
  costs what a one-person value costs (derived from the wrap, not run).
- Outside the lock store but part of the lock design: each value's own row
  carries :lock-id, 67 B logical, which repeats the row's own address under
  per-value grain; it is in both variants, so the differences above exclude it.
- The replication log of the task (task-threads/.../replog, not in the RocksDB
  directory) grew by another 77 to 136 B per value for the lock rows and grew
  linearly throughout; its retention was not observed.

The curve. Logical growth is exactly linear: every step of 10,000 values
adds the same bytes (1,890,000 in base64), because every row is one RocksDB
entry of fixed size (size tracking off, one entry more per value, all in the
subindexed family). Compacted disk growth is linear: the ten steps of each
variant lie within 0.4% of each other for 40-byte values, 0.7% and 1.3% for
200-byte values (raw, base64). The live directory grows linearly while it is
write-ahead log (198 B per value in base64); in the 200-byte lock variants the
memtable flushed near 85,000 values and the WAL stayed pinned on disk beside
the new SST (the default column family's single entry keeps it), so the live
difference jumps to about 620 B per value: flush timing, not lock cost.

Ratio of lock store bytes to value bytes
----------------------------------------
Against the value's plaintext (canonical EDN, 40 or 200 B):
                        logical   compacted disk
  40 B, base64            4.73         2.70
  40 B, raw               4.23         2.17
  200 B, base64           0.95         0.54
  200 B, raw              0.85         0.43
  40 B, two people        5.83         3.70
Against the value rows as the slice stores them without lock rows: 0.38 to
0.75 logical (raw KV) and 0.28 to 0.94 on compacted disk. Against the sealed
value slot alone: 2.01 (40 B, base64), 2.41 (40 B, raw), 0.62 and 0.73 (200 B).

Verdict against the thresholds (main session's assumptions: up to 2x fine;
above 4x, hand layers default to per-act locks or keep locks in the record),
reading "value bytes" as the value's plaintext:
- Values of about 200 B: fine on every measure (0.43x to 0.95x).
- Values of about 40 B: above 4x in logical bytes (4.2x raw, 4.7x base64;
  5.8x for a value marked to die with a second person), between 2x and 4x on
  compacted disk (2.2x, 2.7x; 3.7x).
- Because the cost is a constant per value, the verdict is set by the size
  of hand-layer values. Logically, 2x or less needs values of at least 95 B
  (base64) or 85 B (raw), and above 4x means values under 47 B or 42 B. On
  compacted disk: at least 54 B or 44 B for 2x; under 27 B or 22 B for 4x.
- The two fallbacks do not bring 40-byte values to 2x. Keeping the lock in
  the record saves only the key: 129 B per value in base64 (3.2x), 109 raw
  (2.7x), 89 raw without the nil and empty fields (2.2x), computed from the
  serializer, not run on disk. Per-act locks divide one row (55 B key plus
  the record) by the values per act, so they help only when hand acts carry
  several values. The floor of a per-value GCM-wrapped lock is its 60 raw
  bytes, 1.5x a 40-byte value, before any key or framing.
- Read against the value rows the store already writes, the lock store is
  under 1x everywhere: small values already cost the store about 7x their
  plaintext before any lock row (295 B logical per 40-byte value).

What is uncertain
-----------------
- The size of hand-layer values is unknown, and it decides the verdict.
- Which bytes and which denominator the thresholds mean: plaintext is the
  reading used; against stored value rows every variant is under 1x.
- The slice follows an unvalidated plan. Plan choices set 80 of the 189 B:
  the lock id as key (59 B), the nil :any-blobs (12 B) and empty :any-of
  (9 B); base64 sets another 20 B. A validated or revised plan moves the
  number.
- Disk numbers use the RocksDB options Rama sets on the in-process cluster
  (Snappy, 4 KB blocks, 10-bit bloom filter); a production cluster may
  compress differently. The compacted figure is a floor: a live store adds
  LSM space amplification and a WAL, which here stayed pinned after the
  first flush. Replication factor 1; a real cluster multiplies numerator and
  denominator alike. The replication log's retention was not observed.
- Logical sizes use Rama's internal serializers; they agree with the RocksDB
  key-value bytes to within 3 B per row (the subindex key prefix).
- One value per act; per-act grain and locks-in-the-record were computed, not
  run.

Runs
----
- Smoke runs at 2,000 values (about 10:59 and 11:04:30) found two bench bugs
  (the scan read one column family; the row check assumed a lock row in the
  no-lock variant), fixed; not kept.
- The in-process cluster binds a fixed port, 2002. Two clusters cannot run at
  once on this machine: a collision fails at start ("Address already in
  use"), as the first full attempt did at 11:10:33 against the parallel
  session's stream-bench. The runner then waited for 30 s with no other rig
  bench or test JVM and the port free before every variant, and logged
  overlaps (runs/phase7-lock-growth-overlap.log): none during a cluster of
  theirs; two 6-second report JVMs of theirs during two of my variants.
- First full run 11:12 to 11:42: the compacted measure used compactRange's
  default, which moves a lone flushed file instead of rewriting it; after a
  live flush (200-byte lock variants, about 85,000 values) the per-value
  compacted cost fell from about 110.7 to 103.7 B. The rerun forces the
  rewrite; logical bytes repeated exactly, raw KV within 60 B in 19 MB.
- Every variant of both full runs: 0 append errors, every check as expected.
