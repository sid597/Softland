Phase 7, number 3: one person's layer on one thread, acts per second and
latency. On the stream store as it stands (src/rig/store/, unchanged),
in-process cluster. 25 September 2026.

In-process cluster timings mean orders of magnitude only (rama skill,
testing.md axiom 1). Read every number below that way.

MACHINE
  AMD Ryzen 9 9900X (12 cores, 24 threads), 62 GB RAM, Linux 7.0.0-31-generic,
  OpenJDK 21.0.12.1 (64-Bit Server VM 21.0.12.1+1-1-24.04.4-Ubuntu).
  The cluster's files live under /tmp/ipc<random>/: ext4 on an NVMe SSD
  (WD_BLACK SN850X), not tmpfs. Load average before the runs: 0.43.

CONFIGURATION
  Rama 1.6.0, Clojure 1.12.4. rtest/create-ipc, then launch-module! of
  rig.store.module/Store with {:tasks 4 :threads 4 :workers 1}: a thread per
  task. JVM from the :bench alias: -Xss16m -Xmx16g, default G1. The module's
  stream options are Rama's defaults (nothing set).

METHOD
  Harness: test/rig/bench/stream_bench.clj, function one-thread.
  Command, from the rig folder, one JVM and one cluster per run:
    clojure -M:bench rig.bench.stream-bench one-thread <run-id>
  Reported set: runs 4, 5, 6 (11:22 to 11:30), each started only when no
  other JVM was running and port 2002 was free, with every other JVM seen
  during the run logged every 2 s: none was (runs/phase7-stream-overlap.log).
  Raw output: runs/phase7-one-thread-run{4,5,6}.log (RESULT lines, EDN, each
  window with its wall-clock bounds).
  Summary: clojure -M:bench rig.bench.stream-bench summarize <logs>.

  1. The layer is made with the client: c/make-layer-offer :bench-person
     {:kind :personal :owner :pat}, then c/grant-offer [:pat :bench-person
     :bench-person]; both admitted. The *offers depot is placed by layer
     (hash-by :layer) and the gate topology has no partitioner, so every
     offer into the layer is decided on the one task that holds its depot
     partition.
  2. An act is one fact {:e <one of 1,000 entities in rotation> :k :note
     :v <38-character string>}: the value's canonical text is 40 bytes. No
     replace, nothing stood on, no control fact. Built with c/build as :pat
     citing [:pat :bench-person :bench-person]; the gate writes 4 PStates per
     admitted act (see runs/phase7-agent-rate.txt).
  3. Warmup: 4 offerers for 20 s.
  4. (a) One offerer, sequential acked offers (c/offer!, each waits for its
     ack): 1,000 unmeasured, then 2,000 measured.
  5. (b) K offerers, each a thread in a closed loop with no pause, for
     K = 1, 2, 4, 8, 16, 32 as asked, then 64 and 128 past the asked range
     because the rate was still rising at 32. Each K: 3 s unmeasured, then a
     10 s measured window.
  6. Rate: admitted acts / (window start to the last offerer's last ack).
     Latency: System/nanoTime around c/offer! only, every act in the window,
     percentiles by nearest rank.
  7. Placement, checked in every measured window: which depot partition grew
     and by how much; each task's $$clock before and after (a key per task
     from rtest/gen-hashing-index-keys; each decision stamps at least clock
     + 1, so the deciding task's clock moves by at least the decisions);
     per-thread CPU over the window. Up to 200 sampled admitted acts had
     their answer record, log row and heads row read back.
  8. Median and spread (minimum to maximum) across the three runs.

EVERY OFFER DECIDED ON THE LAYER'S ONE TASK: yes, in all 27 measured
windows of runs 4-6 (per run: (a) and eight K levels), and in all 27 of
runs 1-3.
  - Depot: only partition 1 grew, in each window by exactly the number of
    offers sent; partitions 0, 2 and 3 grew by 0.
  - Clocks: only task 1's $$clock moved, by at least the number of decisions
    (by exactly the act count once the rate passed 1,000/s); tasks 0, 2 and
    3 stayed where they were.
  - Threads: the busiest thread in every window was task 1's task thread
    ("... DTT 1 0-task-group-exec-0").
  - Code: the gate's <<sources block in module.clj has no partitioner, so a
    record's whole event runs on its depot partition's task.
  - Indexes read back: 40 (a) and 60 to 200 (b) sampled acts per window, all
    complete (record yes with the act's stamp, one log row, heads row).

VERDICT against the main session's threshold (at least 100 acts per second
at 20 ms or less at p99; Sid may change it)
  Rule used: far = at least 10x on one side of the threshold (decides);
  near = within 10x (the in-process cluster cannot decide).
  Rate: FAR above once a few acts are in flight: 1,307/s at K=8 (13x) and
  2,228/s at K=16 (22x), with median p99 8.7 and 9.7 ms. One offerer
  waiting for each ack gets 299/s (3.0x), which alone would be near.
  Latency: NEAR. The best p99 is 4.7 ms (one offerer, sequential or K=1),
  4.2x under 20 ms; at K=8 and 16 it is 8.7 and 9.7 ms, about 2x under.
  Within 10x at every K, so the in-process cluster cannot decide the latency
  half; the diagnostic says most of it is this machine's disk flushes, which
  a real cluster changes in both directions.
