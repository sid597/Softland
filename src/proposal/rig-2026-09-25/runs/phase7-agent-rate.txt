Phase 7, number 1: index writes per second with an agent session layer
writing small acts continuously. On the stream store as it stands
(src/rig/store/, unchanged), in-process cluster. 25 September 2026.

In-process cluster timings mean orders of magnitude only (rama skill,
testing.md axiom 1). Read every number below that way.

MACHINE
  AMD Ryzen 9 9900X (12 cores, 24 threads), 62 GB RAM, Linux 7.0.0-31-generic,
  OpenJDK 21.0.12.1 (64-Bit Server VM 21.0.12.1+1-1-24.04.4-Ubuntu).
  The cluster's files live under /tmp/ipc<random>/: ext4 on an NVMe SSD
  (WD_BLACK SN850X), not tmpfs. Load average before the runs: 0.43.

CONFIGURATION
  Rama 1.6.0, Clojure 1.12.4. rtest/create-ipc, then launch-module! of
  rig.store.module/Store with {:tasks 4 :threads 4 :workers 1}: a thread per
  task. JVM from the :bench alias: -Xss16m -Xmx16g, default G1. The module's
  stream options are Rama's defaults (nothing set).

METHOD
  Harness: test/rig/bench/stream_bench.clj, function agent-rate.
  Command, from the rig folder, one JVM and one cluster per run:
    clojure -M:bench rig.bench.stream-bench agent-rate <run-id>
  Reported set: runs 4, 5, 6 (11:18 to 11:23), each started only when no
  other JVM was running and port 2002 was free, with every other JVM seen
  during the run logged every 2 s: none was (runs/phase7-stream-overlap.log).
  Raw output: runs/phase7-agent-rate-run{4,5,6}.log (RESULT lines, EDN, each
  window with its wall-clock bounds).
  Summary: clojure -M:bench rig.bench.stream-bench summarize <logs>.

  1. The layer is made with the client: c/make-layer-offer :bench-agent
     {:kind :agent :owner :ada}, then c/grant-offer [:ada :bench-agent
     :bench-agent]; both admitted.
  2. An act is one fact {:e <one of 1,000 entities in rotation> :k :note
     :v <38-character string>}: the value's canonical text, as the log row
     stores it, is 40 bytes. No replace, nothing stood on, no control fact.
     Built with c/build as :ada citing [:ada :bench-agent :bench-agent].
  3. K offerers, each a thread in a closed loop with no pause: build an act,
     send it with c/offer! (an acked append: returns once the gate's event is
     complete and its writes are visible), take the answer, send the next.
  4. Warmup: 4 offerers for 20 s. Then for K = 1, 4, 16: 3 s at K unmeasured,
     then a 15 s measured window.
  5. Rate: admitted acts / (window start to the last offerer's last ack).
     Latency: System/nanoTime around c/offer! only, every act in the window,
     percentiles by nearest rank.
  6. Checked in every window: every answer (yes, no, error) counted; which
     depot partition grew and by how much; each task's $$clock before and
     after (a key per task from rtest/gen-hashing-index-keys); for up to 200
     sampled admitted acts, the answer record (yes, with the act's stamp),
     the log's one row, and the fact's heads row at that stamp, read back.
     Per-thread CPU over the window (ThreadMXBean).
  7. Median and spread (minimum to maximum) across the three runs.

INDEX WRITES PER ADMITTED ACT: 4 (from module.clj and gate.clj decide*)
  For this act (one fact, no replace, nothing stood on, no control fact),
  the gate's one event on the layer's home task writes:
    1. $$layers [layer :answers name]      the answer record         termval
    2. $$layers [layer :log name]          the act's rows (one row)  termval of
                                           the whole subindexed row vector
    3. $$layers [layer :heads [e k [name 0]]]  the new fact's stamp  termval
    4. $$clock                             the task's last stamp     termval
  Zero writes, for this act, of: :stood-on (one per carried stood-on entry),
  :heads deletes (one per distinct replaced fact), :settings (once if the
  act has setting facts), :permissions (one per granted or revoked pid).
  General count from the code: 1 answer + 1 row vector (f rows) + b stood-on
  + r heads deletes + f heads puts + (1 settings) + p permission rows + 1
  clock. The plan's cost line ("1 + f + 2r + s + p + b no-read sets and one
  clock set", PLAN-stream-store.md) counts 3 for this act; the code also
  writes a heads row for a fact that replaces nothing, which a later replace
  needs.
  Reads per act, for comparison: 4 point reads (the name's record, the
  layer's settings, $$clock, the cited permission row); no heads read.
  Outside the gate's writes, Rama also appends the offer to the *offers
  depot and checkpoints stream progress every so many records.

VERDICT against the main session's threshold (at least 1,000 admitted acts
per second per task with every index written; Sid may change it)
  Rule used: far = at least 10x on one side of the threshold (decides);
  near = within 10x (the in-process cluster cannot decide).
  K=1: 299/s = 0.30x. K=4: 646/s = 0.65x. K=16: 2,249/s = 2.2x.
  NEAR at every K: the in-process cluster cannot decide. Every index was
  written for every sampled act.
  What decides the side is the offerer, not the task: one offerer that waits
  for each ack gets about 300 acts/s, bounded by the ack latency (3.3 ms
  mean), with the task's thread 20 % busy. The same code path on one task
  (number 3's K sweep, a personal layer) reached 1,307/s at 8 offerers and
  5,192/s at 128, still rising, the thread at most 60 % busy: the task's
  capacity on this cluster is at least 5x the threshold, also within 10x.

WHAT THE ACK LATENCY IS MADE OF (diagnostic, not a measurement)
  One extra run under strace (strace -f --seccomp-bpf -ttt -T -y, syncs
  only), function diag: a 5 s window at K=1 and at K=16. Tracing slowed it
  (232 and 1,427 acts/s against about 300 and 2,250 untraced). Output:
  runs/phase7-diag-strace.log; the trace itself was a scratch file.
  At K=1 each acked act made about 6 disk syncs, each about 0.4 ms:
    2.0 per act  fsync     the task thread's replication log (replog)
    1.0 per act  fsync     the *offers depot partition's log segment
    1.0 per act  fdatasync $$layers' RocksDB write-ahead log
    1.0 per act  fsync     $$clock's storage directory
  At K=16, 0.95 syncs per act: Rama's batching shares them. So most of the
  3.3 ms at K=1 is waiting on this machine's disk flushes; the task thread's
  own work is about 0.66 ms per act at K=1 and 0.16 ms at K=16 (derived:
  thread CPU share / acts per second). A real cluster changes this in both
  directions (server disks, replication round trips), which is why the
  verdict above stays open.

OBSERVED ALONG THE WAY
  Stamps run ahead of the wall clock above 1,000 acts/s on a task. Each
  decision stamps at least the task's clock + 1 (ruling 4 as the model's
  hybrid clock), in milliseconds. At K=16 the task's clock ended 20.2 to
  21.1 s ahead of the wall after 18 s at about 2,250 acts/s; the clock's
  movement equalled the act count exactly. Under 1,000 acts/s the stamp
  tracked the wall (2 to 4 ms behind the read-back moment).
  The in-process cluster runs with Rama's default worker configs; the docs
  say pstate.maximal.schema.validations and
  pstate.validate.subindexed.structure.locations should be false in
  production. Not changed or measured here (taken from the docs).
