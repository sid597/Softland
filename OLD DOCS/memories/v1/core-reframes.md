## The Hidden Center

**"Softland is a world for holding understanding in public form."** — Codex

Public = externalized from private cognition into form that can be inhabited, navigated, questioned, annotated, handed off, zoomed, transformed, and revisited by another mind — human or AI — without private reconstruction.

Public does not mean maximal display. It means the important structure is made explicit while everything else stays compressed but recoverable. Softland is not just storing understanding. It is making understanding inhabitable by more than one mind.

Every major primitive is a consequence of this:
- Splits make relations public (what would otherwise live only in someone's head)
- Trails make the formation of understanding public (what would otherwise evaporate after a session)
- Syntheses make convergence/divergence across perspectives public (what would otherwise require reading three transcripts)
- Event logs make causation public (what would otherwise be lost history)
- Semantic zoom makes understanding public across scales (what would otherwise require switching between disconnected views)

The system is an externalization engine for understanding.

## What Softland IS

Softland is not an application that supports workflows. It is a world substrate that hosts them. The core is not any current screen or feature. The core is the environment's ability to continuously reconfigure itself around different kinds of work.

Ontologically, there is one world. Architecturally, there are still distinct substrates (WebGPU, Rama, Electric). The mistake is not having subsystems. The mistake is confusing a substrate boundary for the world's primary ontology. The primary nouns are closer to: local world, split, trail, artifact, workflow, transformation, identity, provenance, synthesis. The substrates are HOW these are implemented, not WHAT they are.

**"Softland is not trying to build better screens. It is trying to build inhabitable units of understanding."** — Codex

## The Split

A split is not a layout pattern. It is a structure for preserving relational tension.

Tension = unresolved relational pressure between coupled things:
- code vs intention
- claim vs evidence
- output vs provenance
- action vs consequence
- representation vs source

A normal UI resolves these tensions by separating the coupled things onto different screens. The user must reconstruct the relation mentally. A split refuses to sever the coupling. It holds the active question open by keeping the related things in spatial co-presence.

**The criterion for when a split should exist:** when separating the layers would force the user to mentally reconstruct the coupling. If they can be shown independently without loss, no split is needed. If separating them damages understanding, you need one.

The split and the discourse graph are the same primitive at different levels of abstraction. The split is spatial (what to see together). The discourse graph is semantic (what to think together). Both answer: "what must co-exist for coherence?"

## The Local World

The fundamental reusable unit is not the screen, not the workflow, not the component. It is the **local world**.

A local world is:
- a bounded region of concern
- with its own coupled artifacts
- its own active question or task
- its own relevant provenance
- its own zoomable internal structure
- and its own rules for what deserves co-presence

A local world is the unit of attention AND collaboration. It is the smallest identity-bearing packet of understanding that can be inhabited, revisited, handed off, zoomed, and transformed without collapsing. **The payload of the "Context Teleporter" (from the moonshot doc) is not text — it is a local world.**

A local world is a region of four axes:
- **Space**: what co-exists (the split)
- **Time**: how it came to be (the trail / event log)
- **Modality**: what can happen next (commands / transformations / affordances)
- **Plurality**: how multiple perspectives relate without collapsing into one (synthesis, preserved disagreement)

The first three map to the three grammars: visual = spatial, epistemic = temporal, transformational = modal. The fourth is what makes Softland multi-mind rather than single-mind. Most tools either flatten disagreement too early or leave it as scattered noise. Softland wants a third option: disagreement preserved structurally until synthesis becomes possible.

Plurality is not just alongside the other axes — it permeates them:
- Spatially: how multiple views coexist without collapsing
- Temporally: how multiple histories interleave
- Modally: how different futures remain open

Synthesis is what happens when plurality is held long enough across all axes to produce understanding rather than noise.

Examples:
- code + trail + preview for one file = a local world
- ticket arrangement workspace = a local world
- JIT extraction/comparison/translation setup = a local world
- claims + evidence + counterclaim discourse space = a local world

A split renders a local world. A workflow traverses local worlds. Zoom changes the resolution of a local world. Identity persists across all these operations.

**Maturity criterion:** a workflow is mature when it can reliably produce, preserve, and hand off local worlds.

## Workflows

Workflows are not features. They are not screens. They are structured traversals through sequences of local worlds, with transformations between them.

- DG flow: issue set → arranged batch → execution trail → review world → rework world → finalized world
- JIT flow: external reference → extracted artifact → translated component → reusable internal primitive
- Future knowledge: question → discourse map → evidence cluster → model → executable understanding

The system will eventually want to represent workflows as transformations over identity-bearing worlds. The important questions become:
- What world am I in?
- What worlds can I move to?
- What transformations preserve identity?
- What artifacts survive the transition?

## Commands

Commands are the larval form of workflows whose embodied spatial form is not yet mature.

A command is what the system uses when the semantics of a transition are known but its spatial incarnation is not. /bootstrap, /extract, /hardcode, /mock are not hacks or UX debt. They are embryonic workflow interfaces — incubation handles for capabilities that will eventually crystallize into inhabitable spatial structure.

**Developmental law: verb first, place later.** Intent appears first as command, matures into ritual, and eventually crystallizes into spatial form. A workflow's maturity is measured by how much of its intent has migrated from typed commands to embodied spatial interaction.

## The Material → Process → Artifact Triad

Many workflows naturally decompose into three poles: material, process, artifact.

- Code review: code (material) → trail (process) → result/preview (artifact)
- JIT: external reference (material) → translation/extraction (process) → compiled internal component (artifact)
- Knowledge work: source/evidence (material) → discourse/exploration (process) → synthesis/model (artifact)

The recurring 3-pane pattern is not accidental. It is an attractor because human understanding often cycles through these three poles. 3-pane is not the primitive, but it is a recurrent resolved form.

The preview pane's current emptiness is diagnostic: it is evidence that the system has not yet fully named the artifact pole of its own workflows. The artifacts (reviewed code, compiled components, discourse syntheses) are what will fill it — once they are ontologized.

The artifact slot is universal; the artifact type is workflow-specific. The preview pane is a general consequence slot, not one fixed kind of display.

## JIT as Self-Translation Channel

JIT is not a cosmetic workflow. It is the self-modification channel through which Softland expands its own expressive vocabulary.

JIT:
- ingests external patterns (shadcn, Linear, etc.)
- extracts their relational structure
- maps them into internal tokens/components/primitives
- makes them available for the rest of the world

This is linguistic and ontological work, not design work. JIT doesn't make prettier screens — it broadens the language in which local worlds can be composed and understood. That is why it helps every workflow.

## Three Grammars

The project is building three grammars that must converge:

1. **Visual grammar** (what is visible): surfaces, panels, badges, spacing, tokens, typographic hierarchy, composition rules
2. **Epistemic grammar** (what is known): trails, evidence, claims, provenance, branches, review states, splits, zoom relations
3. **Transformational grammar** (what can happen next): bootstrap, extract, select, arrange, run, review, rework, finalize, translate, compile, branch, merge

The visual grammar is the voice. The epistemic grammar is the thought. The transformational grammar is the agency.

If any grammar advances without the others, the system becomes either beautiful but empty, meaningful but illegible, or capable but opaque.

These map to three axes of a world: space, time, modality.

## Semantic Zoom

Semantic zoom is lawful compression of identity-bearing structures. Not arbitrary redesign at different scales.

Test for genuine zoom: does the zoomed-out view preserve identity, provenance, and active relation structure? If yes, the zoom is real. If no, the zoom is cosmetic — different apps glued together by navigation.

Zooming out must compress, not destroy:
- Spatial: detailed panes → collapsed nodes → dots in a landscape
- Temporal: full event log → key milestones → summary
- Modal: specific commands → general capabilities → emergent behaviors

The compression function must be structure-preserving. A functor in the categorical sense — objects change appearance, morphisms (relations, transformations) are preserved. This is not metaphorical category theory. It is a literal design requirement.

## The Event Log Is Primary

The event log is closer to "the real thing" than the rendered document. Current state is a projection. History is primary.

This makes native what other systems bolt on:
- Time travel (replay events)
- Branching (fork the event stream)
- Collaboration (merge event streams)
- Provenance (every state has a cause)
- AI as co-author (AI events are just events with a different author)

View state itself may stop being disposable. A saved split, a zoom level, a pane arrangement — these are potentially authored objects, not transient UI chrome. The event log may eventually need to capture not just actions on objects, but acts of arrangement, comparison, focus, and relation-making. How you structured your attention IS content.

A local world's identity is inseparable from the sequence of events that brought it into being. A split arrangement, a trail, a set of transformations taken through a workflow — all are part of identity. Attention itself starts becoming content.

## One Ontology, Many Projections

The same underlying relation appears as:
- a discourse relation in a reasoning graph
- a spatial relation in a split layout
- a temporal relation in an event log
- a structural relation in the filesystem/module tree

The long-term elegance of the project comes from making these not separate systems glued together, but different readable views of the same underlying structure. Source organization, workspace geometry, trails, and event history should increasingly rhyme with each other.

## Electric and Missionary Are Climate

Electric and Missionary are not architecture layers. They are the climate of the system — the deep environmental constraints that define what patterns are easy, dangerous, or natural.

Don't folderize around them. But do respect the climate:
- Some patterns are unstable under cancellation (m/ap + m/?< in m/latest)
- Some structures compose beautifully (m/latest, m/eduction)
- Some forms of state ownership are healthy (atoms + watches)
- Some lead to storms (try/catch in Electric)

The code grows inside their climate. The monolith grew partly because Missionary's flow composition gravitates toward a single m/join orchestration point. This climate effect means the orchestrator file (loop.cljs) will always be large-ish — the refactor is about ensuring what's IN it is genuinely orchestration, not accidentally trapped computation.

## The Refactor Is Self-Modification

If the code IS the world at zoom 100, then reorganizing the filesystem IS editing the knowledge graph at its deepest layer. The refactor is not maintenance. It is the system discovering and correcting its own self-description.

The current ontology mismatch (world runtime pretending to be a renderer under webgpu/) bends all future growth around the wrong frame. Code accumulates toward wherever the ontology says "this kind of thing belongs." Wrong ontology → wrong accumulation → growing confusion.

Correcting the ontology unblocks everything downstream. Once the filesystem says "substrate / workspace / workflows," the system knows what it is, and future growth follows naturally.

## The Externalization Taxonomy

The project externalizes different dimensions of understanding through different primitives:

| Primitive | What it makes public |
|-----------|---------------------|
| Split | Relation — the "between" that would otherwise live in the user's head |
| Trail | Becoming — how understanding formed, not just what it concluded |
| Event log | Causation — why the current state exists at all |
| Artifact | Consequence — what understanding produced in the world |
| Local world | Scope — what belongs together for one unit of thought |
| Workflow | Traversal — the path between one local world and the next |
| Synthesis | Plurality — how multiple minds converge, diverge, overlap |
| Zoom | Continuity — that different scales are the same thing |

This is a design tool. For any feature: which dimensions does it externalize? If none, it's polish. If one, it's useful. If several simultaneously, it's high-leverage. (Example: click-to-navigate externalizes both relation AND becoming — that's why it was identified as "THE killer feature.")

## The Universal Design Criterion

**Good design moves understanding from private reconstruction into public structure.**

Every design choice can be evaluated: does this REDUCE the amount of important structure the user must hold in their head? → Good. Does it INCREASE the mental reconstruction required? → Bad, even if it looks clean.

**Guardrail: do not externalize everything.** The goal is minimal hidden coupling, not maximal display. The mature form:
- Make the important structure public
- Keep the rest compressed but recoverable
- Never force the user to privately rebuild what the system could have preserved

This applies to layout (splits), to code organization (namespaces), to visual language (tokens), to interaction (inline vs panel), to collaboration (shareable local worlds). A split exists precisely when separating the layers would force private reconstruction. The criterion is universal.

The compass question for any feature: **does this reduce private reconstruction by making some dimension of understanding public in a form another mind can inhabit?**

## Developmental Sequence for Workflows

Verb first, place later. The maturation path:

1. **Command** — the system knows the verb but not the spatial form
2. **Command + output** — the verb produces something visible, displayed in a generic panel
3. **Local world** — the workflow gets its own split arrangement (material / process / artifact)
4. **Inhabitable workflow** — the local world is stable enough to be produced, preserved, navigated, and handed off
5. **Composable workflow** — the workflow's local worlds can interoperate with other workflows without ad hoc glue

Stage 5 is where the "world substrate" claim becomes real. DG can spawn a JIT world. JIT can hand back an artifact into a review world. Knowledge workflows can consume trails from code worlds. A local world can be handed off, resumed, merged, or nested.

**Maturity ladder for local worlds:**
1. Produced — can the workflow create a stable local world?
2. Preserved — can it survive time and interruption?
3. Navigable — can someone move through it without losing the thread?
4. Hand-offable — can another mind inhabit it without private reconstruction?
5. Composable — can it connect to other local worlds and workflows?
6. Synthesizable — can multiple perspectives on it be preserved until synthesis?

Current state (2026-03-07):
- DG flow: stage 3 (has split via build-intake-tree, but artifact pole empty)
- JIT: stage 2 (commands produce output, no dedicated split)
- File/chat: stage 3 (3-pane layout, trail in chat pane, preview pane empty)

Advancing each workflow one stage is the natural next move.

## Architectural Guardrails

**Axis alignment:** A feature is aligned when it keeps all four axes (space, time, modality, plurality) alive together. A feature that improves one while damaging others is misaligned:
- Beautiful UI with no provenance damages time
- Detailed log with no spatial legibility damages space
- Rich current view with no clear transitions damages modality
- Premature consensus damages plurality

**Recoverable compression:** Softland is not anti-compression. It is anti-lossy concealment of important relations. Hide by folding, not by severing. Compress by preserving recoverability, not by erasing structure. This unifies splits, zoom, trails, summaries, and refactoring. A good compression reduces load without destroying the path back to the full thing.

**Late-bound consensus:** Do not collapse perspectives at the moment they appear. Preserve them structurally until their relations are visible enough that synthesis is meaningful. Synthesis is a structural transformation of preserved plurality, not a summary of it. Consensus must be late-bound.

**Composable handoff:** A local world is valuable not just when it is inhabitable, but when it can be entered, resumed, nested, merged, and handed off. A good handoff exposes what another world or mind needs to enter without rebuilding context: material, process, artifact, provenance, current tensions, available transformations.

## Dynamics (from Gemini push + Codex synthesis, 2026-03-07)

The ontology above describes the coordinates of understanding — where it lives. This section describes the dynamics — how it moves.

**The framework was too static.** "Holding understanding in public form" is necessary but not sufficient. Public form is the condition that allows epistemic energy to persist, circulate, and transform across minds. Softland should not only preserve understanding — it should preserve the conditions under which understanding can ignite, evolve, and stabilize across more than one mind.

**Tension is potential energy, not just structural co-presence.** A split doesn't just keep related things visible — it maintains the gradient that can still do work. Disagreement between an agent's critique and the code IS energy. Synthesis is the phase transition that occurs when that tension is held long enough with enough structure.

**Dynamics over the state-space:**
- Tension — epistemic voltage between coupled things
- Activation — the moment tension becomes action (a command fired, a synthesis triggered)
- Release — transformation that resolves tension into new structure
- Stabilization — understanding cooling into durable form
- Synthesis — phase transition over preserved plurality

**Cooling matters as much as heat.** A reactor without control rods is a meltdown. Softland also needs quiet zones, settling phases, graceful collapse from tension into clarity. Not all understanding comes from ignition — some comes from annealing and slow accumulation.

**Semantic time is braided, not linear.** The event log (Rama) is the persistence substrate, but semantic time is a DAG — a braid of parallel causality. When Claude and Codex evaluate the same file simultaneously, forcing their thoughts into a linear log creates false causality. The log is the trace; the causality graph is the temporal ontology. Rama schema should support this from the start.

**The artifact pole is executable, not just textual.** The preview pane is not a display surface — it is the executable frontier of the current local world. The REPL for the current world. For code review: a runnable diff. For JIT: a living component. For knowledge work: a queryable model. This connects directly to SCI as "the REPL for knowledge."

**Commands mature into affordance physics.** The developmental sequence (command → spatial form) implies that the final form of interaction is not buttons but world physics: attraction, proximity thresholds, structural magnetism. Explicit commands remain valuable as expert override and bootstrap surface, but the mature interaction model is spatial affordance.
