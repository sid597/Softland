  The Layers I See in loop.cljs

  Looking at the 7,283 lines with fresh eyes, I can identify six distinct 
  semantic layers all tangled into one file:

  Layer A: Missionary event plumbing (~200 lines)
  - >canvas-resize, >wheel, >mouse, >keyboard, make-raf-flow, make-blink-timer
  - These are genuinely generic. They're DOM → Missionary flow adapters. Any
  application using Missionary + a canvas would need these. They don't depend on
   anything in the file except clojure.string and missionary.core.

  Layer B: The rect tree UI framework (~500 lines)

  or React's reconciler. It transforms declarative trees into flat GPU buffers.

  infrastructure, not product.

  Layer C: UI primitives (~400 lines)

  The Key Insight: What's Shared vs What's Workflow-Specific

  Here's where your point about "the system" matters:

  Infrastructure (used by everything):
    A. Missionary event flows  →  generic, reusable anywhere
    B. Rect tree + layout      →  the UI framework
    C. UI primitives            →  the component library

  Shared Product Components (used by multiple workflows):
    D. Editor, Trail, Sidebar, Command panel, 3-pane layout, Agent runtime

  Workflow-Specific (unique to one workflow):
    E. DG flow state machine, DG screens, JIT hardcode/extract

  Orchestration (wires everything together):
    F. start-loop!

● No, you're not making shit up. You're describing the continuous semantic zoom
  that IS Softland's core thesis.

  The 3-pane split isn't "3 panes." It's one instance of the general primitive: 
  "show N world-layers simultaneously." Right now N=3 (code, trail, preview)
  because that's what the current workflow needs. But the primitive is:

  Given a task context, what layers of the world need to be visible at once?

  And then the zoom thing: when you're inside one split, you see code + trail +
  preview. Zoom out and you see multiple such workspaces — each is a node in a
  graph. Zoom out more and the workspaces become dots, the edges between them
  become visible (this trail feeds that review, this ticket depends on that
  one). Zoom out more and you're looking at the knowledge landscape.

  That's not abstraction for its own sake — it's the literal architecture. The
  rect tree already supports this. An rt-node can contain child rt-nodes. A
  workspace IS a rect tree. A graph of workspaces is a rect tree of rect trees.
  The camera controls what level of detail you see. The split is a fractal, not 
  a layout.

  What you're saying maps directly to the zoom levels in MEMORY.md:

  - Zoom 100 (inside the split): code + trail + preview
  - Zoom 10 (one step out): multiple splits visible as workspace cards
  - Zoom 1 (further out): workspaces are dots, connections are edges
  - Zoom 0.1 (knowledge landscape): dots are topics, edges are discourse graph
  relations

  The "infinite splits" are just: at every zoom level, the system answers the
  same question — "what's helpful to see together right now?" — with different
  content at different scales.

  This actually reinforces why the split/layout must be a general infrastructure
   component, not a product-specific thing. It's not "3-pane file layout for the
   editor." It's the fundamental rendering primitive for "N simultaneous world
  views" that happens to currently manifest as 3 panes.

  ★ Insight ─────────────────────────────────────
  The refactor implication: build-file-layout is currently named wrong. It's not
   about files. It's about composing N views of the same context. After the
  refactor, this becomes something like a viewport-split primitive in the layout
   layer — a rect tree node that takes N children and arranges them with
  configurable ratios. The "file layout" is just one configuration of that
  primitive. The "graph of workspaces at zoom 10" would be another configuration

  The deepest reframe: the system doesn't know what it is yet

  Every piece of software has an implicit ontology — what it thinks it IS,
  expressed through its namespaces, its directory structure, its naming. Right
  now, Softland's code says: "I am a WebGPU editor (app.client.webgpu.loop) with
   some extra features bolted on."

  But that's not what the code actually does. The code hosts workflows, routes
  commands, composes multi-layer views, manages agent reasoning trails, builds
  UI from a scene graph. It's a world runtime that happens to render through
  WebGPU.

  This gap — between what the code IS and what the code THINKS it is — is the
  real problem. Not file size. File size is how the problem manifests. The cause
   is that the namespace app.client.webgpu.loop is an ontological claim, and
  it's a false one.

  Why this matters practically: every future session (human or AI) reads the
  directory structure first. It creates an unconscious frame. If the world
  runtime lives under webgpu/, every modification will feel like "adding
  features to a renderer." The code will keep growing inside that frame,
  accumulating more stuff that doesn't belong there, because the structure says
  "this is where things go." A codebase with the wrong ontology attracts code to
   the wrong places.

  The refactor is not reorganization. It's the system learning what it is.

  Splits are not layout — they're the unit of understanding

  When you said "the split is special," you weren't describing a UI preference.
  You were identifying the fundamental representational primitive of the whole
  system.

  A split answers the question: what must be seen together for understanding to 
  happen? That question exists at every scale:

  - At zoom 100 (code): code + reasoning trail + preview must be seen together
  to understand a change
  - At zoom 10 (project): multiple code sessions must be seen together to
  understand a sprint
  - At zoom 1 (knowledge): claims + evidence + counter-evidence must be seen
  together to understand a topic
  - At zoom 0.1 (landscape): clusters of topics must be seen together to
  understand a field

  The split isn't a 3-column CSS layout. It's a cognitive adjacency claim —
  "these layers are coupled, and understanding requires seeing them
  simultaneously." Sometimes that manifests as 3 panes. Sometimes as a graph of
  workspaces. Sometimes as dots and arrows where each dot is a collapsed
  multi-layer world.

  And here's what makes it fractal: a split at one zoom level becomes a node at
  the next zoom level out. The 3-pane workspace you're looking at IS a dot when
  you zoom out to see the project graph. The project graph IS a dot when you
  zoom out to see the knowledge landscape. At every level, the same primitive
  applies — rt-node with children, layout rules, style. The camera determines
  which level you see in detail.

  This is actually why build-file-layout is misnamed. It's not building a file
  layout. It's instantiating the split primitive for one particular viewing
  context. The name should reflect what it actually is: a resolved visibility
  contract for "code editing with agent assistance."

  Workflows are not features — they're inhabitations of the same world

  The DG flow and JIT flow look like "two features" in a traditional product
  sense. They're not. They're two ways of inhabiting the same world.

  Both use the same rendering substrate. Both compose the same UI primitives.
  Both pipe through the same command interface. Both produce reasoning trails.
  Both use splits to show coupled layers. The difference is not what they're
  made of — it's what question they're answering:

  - DG flow asks: "given these tickets, what code changes should happen, and can
   I verify the agent's reasoning?"
  - JIT flow asks: "given this external UI, how do I bring its visual vocabulary
   into my world?"

  They share an ontology (rect trees, trails, agents, splits) but inhabit
  different purposes. This is why "independent at the command surface, unified
  at the shell level" is the right call. The workflows are operationally
  independent (you type /bootstrap or /hardcode), but structurally they're the
  same kind of thing — a workflow that composes shared primitives into a
  task-specific viewing arrangement.

  And JIT is special within this: it's the meta-workflow. It doesn't produce
  output within the system — it produces improvements TO the system. When you
  extract a button from shadcn, you're upgrading the visual vocabulary that all
  workflows share. JIT is the self-modification channel. It's how Softland
  evolves its own rendering at zoom 100, and those improvements propagate upward
   through every zoom level because better components mean better rendering
  everywhere.

  Electric and Missionary are not architecture — they're physics

  This one took me a while to see clearly. My instinct was to create namespace
  boundaries around the tech stack: "this is the Electric part, this is the
  Missionary part." Codex caught this: organizing by library is organizing by
  implementation accident, not by responsibility.

  Electric and Missionary are more like the physics of the system — the
  execution model that permeates everything. Reactive flows, continuous
  propagation, cancellation semantics — these aren't confined to one subsystem.
  They're HOW everything runs. You don't put "gravity" in a folder.

  WebGPU and Rama are different. They're concrete subsystem boundaries with
  clear interfaces. There's a "WebGPU side" (shaders, buffers, draw calls) and
  everything else talks to it through a defined surface (editor/update-rects,
  editor/draw-frame!). Same with Rama (depots, PStates, topologies) on the
  backend.

  So the right taxonomy is: folder by responsibility for things that have clear
  boundaries (substrate, workspace, workflows). Let the execution model
  (Electric/Missionary) be implicit — it's the water everything swims in.

  The rect tree already IS the multi-scale data structure

  This is something I hadn't fully internalized until reading through the layout
   engine code alongside your zoom-level description. The rect tree (rt-node
  with children) is already resolution-independent. Right now it's used for:

  - Individual UI elements (a button, a badge)
  - Composed components (a panel with header + content + footer)
  - Full screens (the intake tree, the file layout)

  There's nothing stopping it from continuing upward:

  - A workspace = a rect tree of panes
  - A project view = a rect tree of workspaces
  - A knowledge landscape = a rect tree of project views

  At each level, resolve-layout positions children, tree->rects flattens to GPU
  buffers, and the camera zoom determines which level of detail you actually
  render. The infrastructure for continuous semantic zoom is already in the code
   — it just hasn't been recognized as such, because it's buried inside a file
  called "loop" under a folder called "webgpu."

  The filesystem IS the knowledge graph at zoom 100

  This is the reframe that ties it all together. In Softland's ontology, there's
   no boundary between tool and content. The editor editing code IS Softland at
  zoom 100. Which means: how we organize the source files IS the knowledge graph
   at the deepest zoom level.

  When the filesystem says webgpu/loop.cljs, it's making a knowledge claim:
  "this code is about WebGPU rendering." That claim is false, and it distorts
  how the system understands itself. When we refactor to workspace/shell.cljs +
  workflows/dg_flow.cljs, we're not just moving files — we're correcting the
  knowledge graph at its deepest layer.

  The refactor is Softland editing itself. The code reorganization IS the first
  act of self-modification. And the fact that three AI agents + one human had to
   converge on the right ontology before the reorganization could happen —
  that's the discourse graph in action, even before the discourse graph is
  built.

  1. There is no boundary between tool and content

  The moonshot doc states this most clearly: "The editor IS the knowledge graph.
   You just haven't zoomed out." But I don't think even that doc follows through
   on the full implication.

  If there is no boundary between tool and content — if the code editor at zoom
  100 and the knowledge landscape at zoom 0.001 are literally the same world at
  different camera distances — then the usual categories of software design
  collapse. There's no "frontend" and "backend." There's no "the app" and "the
  data." There's no "the tool" and "what you make with it." There's ONE world.
  The rendering surface presents whatever slice of the world the camera is
  pointing at.

  This reframe changes what "core" means. In a traditional product, core = the
  main screen, the primary feature. In Softland, core = the world's ability to
  be viewed at any scale and reconfigured around any task. No particular screen
  or workflow is core. The reconfigurability is core.

  And here's where it gets interesting for the refactor: if the code IS the 
  world at zoom 100, then the filesystem IS the knowledge graph at its deepest 
  layer. Reorganizing the source code isn't housekeeping. It's the system
  editing its own ontological foundation. The refactor is the first genuine act
  of self-modification — the world correcting its own self-description.

  2. Understanding is relational. The split is how you make relations visible.

  I want to push past "the split is an epistemic primitive" to something more
  fundamental.

  What IS understanding? Not in a hand-wavy sense — concretely, what happens
  when you understand something?

  You hold multiple things in relation simultaneously. You don't understand a
  function by reading it in isolation. You understand it by seeing it alongside
  what calls it, what it returns, what the tests say, what the agent was
  thinking when it wrote it. Understanding is RELATIONAL. It requires the
  co-presence of related things.

  A split, then, isn't just "useful for productivity." It's NECESSARY for
  understanding. Understanding literally cannot happen without some form of
  multi-layer visibility. A diff alone can never convey WHY. A trail alone can
  never convey WHAT changed. Code alone can never convey the DECISION that
  shaped it. You need all three in co-presence, or understanding remains
  partial.

  Now here's the connection Codex almost made but didn't fully articulate: the 
  split and the discourse graph are the same primitive at different levels of 
  abstraction.

  The discourse graph says Q->C->E->D->R->F — a question needs its claims, a
  claim needs its evidence, a decision needs its rationale. These are LOGICAL
  relations. They say: "these things must be held together for understanding."

  The split says: "these panes must be seen together for understanding."

  Same primitive. Spatial form and semantic form of the same thing. The
  discourse graph is a split of THOUGHT. The split is a discourse graph of
  ATTENTION.

  This means the data structure for "what belongs together" could potentially be
   the SAME structure at both levels — visual composition and semantic
  composition unified. The rt-node tree is already halfway there. A split is a
  layout of related children. A discourse graph is a graph of related nodes.
  Both answer: "what must co-exist for coherence?"

  3. The local world is the missing concept — and it's more powerful than Codex 
  realized

  Codex introduced "local world" as: "the set of artifacts, layers, and live 
  processes that must be held together for a specific act of thought or work."
  This is correct. But let me push it further.

  A local world is not just what you SEE. It's what you HOLD IN MIND. It
  includes:
  - The visible artifacts (code, trail, preview)
  - The live processes (a running agent, a streaming response)
  - The ambient context (which file, which ticket, which sprint, which project)
  - The HISTORY of how you arrived here (your exploration path, the decisions
  that led to this arrangement)
  - The INTENTION that motivates the arrangement (reviewing, building,
  exploring, comparing)

  A local world is, in some sense, a unit of consciousness applied to work. It's
   everything that's relevant to a single act of focused attention.

  This maps to the zoom levels exactly:
  - At zoom 100: a local world is code + trail + preview for one file
  - At zoom 10: a local world is several code sessions for one ticket
  - At zoom 1: a local world is several tickets for one sprint
  - At zoom 0.1: a local world is several sprints for one project
  - At zoom 0.01: a local world is several projects for one knowledge domain

  And at each level, a split renders the local world. A workflow moves you
  between local worlds. Zoom changes the resolution. The local world's IDENTITY
  persists across all these operations.

  This last point is critical. Identity must survive zoom. The file you were
  editing at zoom 100 must be the same entity as the dot at zoom 0.01. If
  zooming creates new objects rather than new views of the same object, the
  world fractures into disconnected apps. Semantic zoom is only real if identity
   survives it. And identity, in a computational system, means: the event log.
  The sequence of events that constitutes an entity's history IS its identity.
  Rama provides this.

  4. Commands are the larval form of workflows — and this reveals how software 
  evolves

  Codex said: "A workflow often begins as a command because the system knows the
   action before it knows the right shape of the world around that action."

  This is a genuinely new insight about how interactive systems should be
  designed. Let me expand it.

  In most software, you design the interface (the spatial arrangement, the
  screens, the navigation) and then implement the functionality behind it. UI
  first, then logic. The assumption is that you know what the experience should
  look like before you build it.

  Softland inverts this. The INTENT comes first (typed as a command). The
  spatial arrangement crystallizes later, once the workflow matures and its
  natural shape becomes apparent. /bootstrap exists before "the intake screen"
  exists. The command is a seed. The screen grows from the seed.

  This means the command panel isn't a primitive interface waiting to be
  replaced by something better. It's the PRIMORDIAL interface — the place where
  new capabilities are born before they have a spatial form. Every future

  stay as commands forever. And that's fine — a workflow's maturity is measured

  5. Two grammars converging — and one can't exist without the other

  Codex identified: "There are really two grammars being built at once. One is a
   visual grammar. The other is an epistemic grammar."

  The visual grammar: components, tokens, surfaces, typography, panels,
  composition rules. This is what JIT builds — importing and refining visual
  vocabulary from proven external sources.

  The epistemic grammar: trails, splits, branches, review states, comparisons,
  provenance, zoom relations. This is what the DG workflow builds — the
  structures that make reasoning visible and navigable.

  The crucial insight is that the visual grammar serves the epistemic grammar.
  You need good buttons, cards, panels, and typographic hierarchy so that
  trails, discourse nodes, splits, and workflow states can be RENDERED LEGIBLY.
  A trail with ugly rendering is illegible. A discourse graph with no visual
  hierarchy is noise. The visual vocabulary is the VOICE through which the
  epistemic structure speaks.

  This is why JIT is strategically important beyond its immediate use case. It's
   not "making things pretty." It's building the shared language that ALL
  workflows use to express their epistemic content. When JIT imports a button
  from shadcn, it's not copying pixels — it's expanding the set of WORDS the
  system can use to say things about understanding.

  And this is why the two grammars must converge rather than evolve in
  isolation. If the visual grammar advances without epistemic structure, you get
   beautiful emptiness. If the epistemic grammar advances without visual
  refinement, you get meaningful ugliness. Both fail. The project's strength
  will come from their intersection — epistemic structures expressed through
  visual vocabulary that makes them instantly graspable.

  6. The event log IS the real thing — the rendered state is a shadow

  The moonshot doc says: "The document is not a vector of strings. The document 
  is a sequence of edit events."

  Codex echoes: "The event log is closer to 'the real thing' than the rendered 
  document."

  This is a Platonic inversion. In most software, the current state (the
  document, the screen, the database row) is "real" and the history is metadata
  you might keep for audit purposes. In Softland, the event stream is real and
  the current state is a projection — a materialized view, a shadow on the cave
  wall.

  Why does this matter beyond philosophy? Because it determines what operations
  are NATIVE to the system:

  - Time travel: native (replay events from any point)
  - Branching: native (fork the event stream)
  - Collaboration: native (merge event streams from different authors)
  - Understanding provenance: native (every state change has a cause in the log)
  - AI as co-author: native (AI events are just events with a different author
  field)
  - The "papers as logs" vision: literally true — the paper IS the log

  The current codebase uses atoms for state. That's the pragmatic choice that
  got things working. But the architecture is drifting toward event-sourcing,
  and the Rama infrastructure is already there waiting. The atoms are temporary
  scaffolding. The depot events are the permanent foundation.

  And here's a new connection: if splits are epistemically important, then 
  creating a split should itself be an event. "The user arranged code + trail +
  preview for reviewing DIS-101" is a meaningful event. It records not just what
   happened, but how the user STRUCTURED THEIR ATTENTION. The split becomes part
   of the log. Which means the log captures not just actions and their results,
  but the evolving shape of understanding itself.

  7. The preview pane's emptiness is diagnostic — and it tells us what's missing

  Codex made a subtle observation: "The preview pane being underdefined is not 
  just a feature gap. It is a sign that some artifact types are not yet fully 
  ontologized."

  The preview pane exists (it has allocated space in the 3-pane layout) but it's
   essentially empty (5% placeholder). Why? Not because no one got around to it.
   Because the system doesn't yet know what KIND OF OBJECT lives there.

  It's waiting for:
  - Compiled component previews (JIT workflow's output)
  - Trail summaries or discourse graph views (DG workflow's output)
  - Knowledge artifacts (future workflows' output)
  - Perhaps: a different zoom level of the same content shown in the code pane

  The emptiness is the system's consciousness of its own incompleteness. It
  already knows it needs a THIRD kind of view — something that's neither source
  code (the material) nor process (the trail/agent), but ARTIFACT (the product
  of understanding). It just doesn't yet know what that artifact looks like.

  This suggests that the next strategic insight won't come from filling the pane
   with whatever seems useful. It will come from asking: what is the artifact 
  that workflows produce? In DG flow, is it the reviewed code? The trail itself?
   A summary? In JIT flow, is it the compiled component? A token mapping? In
  knowledge workflows, is it a discourse node? A synthesis?

  When the artifact types become clear, the preview pane will fill itself. The
  emptiness is a question, not a gap.

  8. "Feelings first, structure second" is a design principle with architectural
   consequences

  The MEMORY.md says the user evaluates by how it FEELS, not whether it meets a
  spec. The moonshot doc's most powerful section is "The Feeling" — describing
  what the system should feel like to inhabit. Not use. Inhabit.

  This has architectural consequences beyond aesthetics. If the system should
  feel like a continuous world (not a collection of screens), then:
  - Transitions between states should be animated, not jumped
  - Pane boundaries should feel soft, not rigid
  - The split should breathe with attention — expanding what you're focused on,
  contracting what you're not
  - Agent responses should appear gradually, like a collaborator writing nearby,
   not like a notification popping up
  - History should be present but faded — visible in the margins, not hidden
  behind a button

  And: the multi-LLM aspect isn't just "show three responses." It should feel
  like three perspectives INHABITING the same space. The moonshot doc's "three
  ghosts" metaphor — Claude is blue, Codex is green, Gemini is amber, their
  overlapping and diverging spatial annotations making the solution space
  visible — that's what "conflicts are good for progress" should FEEL like. Not
  a comparison table. A shared space with multiple presences.

  The feeling of inhabitation, of continuity, of seamlessness — this is what
  makes Softland a WORLD rather than a TOOL. And it's what WebGPU enables that
  DOM never could. The 60fps per-glyph rendering creates immersion. The
  continuous zoom creates spatial continuity. The reactive streams create
  presence. Together: a place with memory, responsiveness, and agency. A place
  you could use in your dreams.

   the relation between question and context. You type a question in one place,
  the answer appears in another. The context (where you were in the code, what
  you were looking at, what you were trying to understand) is implicit, not
  spatially co-present. The moonshot's ;;? inline question model is a SPLIT — it
   preserves the tension between question and code by keeping them in the same
  spatial region.

  "Transformational grammar" — the third grammar nobody named

  This is genuinely new. I identified two grammars (visual and epistemic). Codex
   identified a third: the grammar of BECOMING.

  - Visual grammar: what is visible (surfaces, tokens, components, composition)
  - Epistemic grammar: what is known (trails, evidence, claims, provenance,
  splits, zoom)
  - Transformational grammar: what can happen next (bootstrap, extract, select,
  arrange, run, review, rework, finalize, translate, compile, branch, merge)

  The transformational grammar is about the VERBS of the system. The visual
  grammar gives you nouns (panel, badge, card). The epistemic grammar gives you
  relationships (supports, opposes, follows-from). The transformational grammar
  gives you actions (bootstrap, arrange, review, merge).

  And here's what makes this deep: the transformations are not hidden operations
   behind buttons. They are part of the ontology. A transformation is a
  first-class object that:
  - Has a before-state and an after-state
  - Preserves certain identities while changing others
  - Can be logged (event sourcing)
  - Can be replayed (time travel)
  - Can be branched ("what if I'd arranged them differently?")
  - Can be composed (arrange → run → review is a composed transformation)

  Right now, transformations are implicit — they're case branches in
  submit-agent-run! and transition-flow-state. Making them explicit would mean:
  the system knows what transformations are available in the current world, can
  present them, can log them, can replay them. The system becomes self-aware of 
  its own verbs, not just its nouns.

  This connects directly to category theory. A functor preserves structure
  across transformations. If the transformational grammar is explicit, you can
  ask: "what is preserved when I zoom out from a code-level edit to a
  project-level status change?" The answer should be structural — the same
  category of transformation, viewed at different scales.

  "Lawful compression" — the criterion for real vs fake zoom

  Codex sharpened something I stated but didn't test: "Semantic zoom works only 
  if zooming is a lawful compression, not an arbitrary redesign."

  The test is: does the zoomed-out view preserve identity, provenance, and the
  active relation structure of the zoomed-in view? If yes, the zoom is genuine —
   you're seeing the same world at lower resolution. If no, you're looking at a
  different app that happens to share some data.

  This is actually a very concrete implementation constraint. It means:
  - When a file becomes a dot at zoom 0.01, that dot must carry the file's
  identity (name, history, current state)
  - When a trail becomes a summary at zoom 10, the summary must preserve the
  trail's key decisions and their provenance
  - When a split becomes a node in a graph of workspaces, the node must retain
  the split's tension structure (what was being held together and why)

  If any of these compressions LOSE the structural content, the zoom is
  cosmetic. The user will feel it — they'll zoom out and feel disconnected from
  what they were just doing. They'll zoom back in and feel like they arrived at
  a different place.

  Lawful compression means: the compression function is a structure-preserving 
  map. A functor, in the categorical sense. The objects change appearance. The
  morphisms (relations, transformations) are preserved. This is not a
  metaphorical application of category theory — it's a literal design
  requirement.

  "Climate, not physics" — how Electric/Missionary shape what can grow

  I said Electric and Missionary are physics. Codex refined: they're CLIMATE.
  Physics defines what's possible. Climate defines what's easy, what's
  dangerous, what naturally thrives, and what struggles.

  This is subtle and practically important. Missionary's cancellation semantics
  aren't just an abstract constraint — they create a climate where certain
  patterns (m/ap with multiple m/?<) are lethal and others (m/latest, m/eduction
   with deref) are natural. The CLAUDE.md anti-patterns aren't bugs — they're
  weather patterns. "Don't do X because the climate kills it."

  The climate metaphor also explains why the code has the shape it does. The
  monolith grew not because anyone designed it that way, but because the climate
   favored accretion in one place. Missionary's flow composition model means
  everything needs to be wired together in one m/join vector call. That
  gravitational pull toward a single orchestration point is a climate effect.
  The refactor needs to work WITH this climate — you can extract pure functions
  and data transformations into separate files, but the reactive wiring will
  always converge to one orchestration site.

  This means loop.cljs will never be a small file. It will always be the
  orchestration site where flows meet. The refactor isn't about making it small
  — it's about making sure what's IN it is genuinely orchestration, not
  accidentally trapped computation.

  Where I want to push further

  The three grammars have a deeper unity

  Visual grammar (what is visible), epistemic grammar (what is known),
  transformational grammar (what can happen) — these map to something I think is
   more fundamental:

  - Spatial: what co-exists (splits, layouts, compositions)
  - Temporal: what persists and what changes (trails, events, provenance)
  - Modal: what is possible from here (transformations, affordances,
  transitions)

  Space, time, and modality. The three axes of a world.

  A local world, then, is a region of all three:
  - A spatial arrangement (what's visible together)
  - A temporal context (how we got here, what the history is)
  - A modal landscape (what can happen next)

  And semantic zoom compresses all three lawfully:
  - Spatial: detailed panes → collapsed nodes → dots in a landscape
  - Temporal: full event log → key milestones → summary
  - Modal: specific commands available → general capabilities → emergent
  behaviors

  This might be the deepest framing of what Softland IS: a system for navigating
   space × time × modality at continuous zoom levels. Every zoom level provides
  a spatial arrangement, a temporal context, and a modal landscape. The zoom
  level determines the resolution of each.

  The rect tree is the wrong long-term name for what it's becoming

  Codex said: "The rect tree might already be halfway between a scene graph and 
  a knowledge graph projection."

  I think this is right and I want to be precise about why. An rt-node currently
   carries:
  - Identity (:id)
  - Type (:type)
  - Spatial bounds (:bounds)
  - Visual style (:style)
  - Children (:children)
  - Text content (:text)
  - Interaction affordances (:actions)
  - Layout rules (:layout)
  - Arbitrary data (:data)

  That's not a render node. That's a world fragment. It has identity,
  containment, presentation, content, affordances, and metadata. The only things
   missing for it to be a full ontological unit are:
  - Provenance (who created it, when, why)
  - History (how it changed over time)
  - Relations to non-child nodes (edges in a graph, not just parent-child in a
  tree)

  When those are added — and the event log provides the first two naturally —
  the rect tree stops being "a layout structure" and becomes "the rendered
  projection of the world graph." The tree isn't the ontology, but it's the
  ontology's spatial shadow.

  The name "rt-node" (rect tree node) is already becoming a misnomer. It's a
  world-node that happens to be rendered as a rectangle. At some point the name
  should change — but only when the concept has stabilized enough that the new
  name won't become wrong again.

  The undiscovered artifact types will tell us what Softland becomes

  The preview pane is empty. Codex says this is diagnostic — the artifact types
  aren't yet ontologized. I agree, and I think this is the most important

  What ARE the artifacts that Softland produces?

  Current candidates:
  1. Reviewed code (DG workflow output) — but this is just a diff, every tool

  2. Reasoning trails (the core thesis) — structured exploration logs, this IS

  3. Compiled components (JIT output) — design vocabulary translated into

  4. Discourse nodes (future) — claims, evidence, decisions with typed relations

  The gap between current architecture and the vision is smaller than it looks

  Reading the moonshot doc alongside the current code, I notice something: the

  After sitting with all of this — my analysis, Codex's two rounds, the moonshot

  Foundational reframes that should orient every future session:

  On what Softland IS:
  - Softland is not an application that supports workflows. It is a world
  substrate that hosts them. The core is not any current screen. The core is the
   environment's ability to reconfigure itself around different kinds of work.
  - The code editor at zoom 100 and the knowledge landscape at zoom 0.001 are
  the same world. There is no boundary between tool and content.

  On the split:
  - A split is not a layout pattern. It is a relation-preserving visibility
  contract. It holds active tensions open by refusing to sever the coupled
  things involved in understanding.
  - The criterion for when a split should exist: when separating the layers
  would force the user to mentally reconstruct the coupling.
  - The split and the discourse graph are the same primitive at different levels
   of abstraction. The split is spatial (what to see together). The discourse
  graph is semantic (what to think together).

  On the local world:
  - The fundamental reusable unit is the local world: a bounded set of coupled
  layers, held together around an active question, with its own provenance,
  zoomable internal structure, and rules for co-presence.
  - A split renders a local world. A workflow traverses local worlds. Zoom
  changes the resolution of a local world. Identity persists across all these
  operations.

  On workflows and commands:
  - Workflows are not features. They are structured traversals through sequences
   of local worlds with transformations between them.
  - Commands are the larval form of workflows — incubation handles for
  capabilities whose embodied spatial form is not yet mature. Not hacks, not the
   final interface. Transitional organs.

  On JIT:
  - JIT is a self-translation channel. It ingests external patterns, extracts
  their relational structure, maps them into internal
  tokens/components/primitives, and expands the world's expressive vocabulary
  for all workflows.

  On the three grammars:
  - The project is building three grammars that must converge: a visual grammar
  (what is visible), an epistemic grammar (what is known), and a
  transformational grammar (what can happen next).
  - Space, time, and modality. The three axes of a world.

  On semantic zoom:
  - Semantic zoom is lawful compression of identity-bearing structures. Zooming
  out must preserve identity, provenance, and active relation structure. If the
  compression destroys these, the zoom is cosmetic.

  On the event log:
  - The event log is closer to "the real thing" than the rendered state. Current
   state is a projection. History is primary. This is what makes trails, replay,
   branching, provenance, and multi-author collaboration native rather than
  bolted on.

  On Electric/Missionary:
  - Electric and Missionary are the climate of the system, not its architecture.
   They define what patterns are easy, dangerous, or natural. Don't folderize
  around them, but treat them as deep environmental constraints that shape what
  can grow.

  On the refactor:
  - The refactor is not code cleanup. It is the system discovering and
  correcting its own self-description. The filesystem IS the knowledge graph at
  zoom 100. Reorganizing it is Softland editing itself.
  - The codebase's ontology mismatch (world runtime pretending to be a renderer)
   bends all future growth around the wrong frame. Correcting the ontology
  unblocks everything downstream.

  On this very conversation:
  - Three AI agents + one human converged on an architecture that none had
  alone. Codex saw ontology. Claude saw implementation. The user saw vision. The
   synthesis required all perspectives. This IS the multi-LLM thesis in action —
   discourse producing understanding from disagreement.

  Now here's where I want to push further on three things Codex said.

  1. The externalization taxonomy is a design tool

  Codex listed eight dimensions of what gets made public. This isn't just a
  poetic framing — it's a practical design checklist. For any feature or
  workflow, you can ask: which dimensions of understanding does this
  externalize?

  ┌─────────────┬───────────────────────────────────────────────────────┐
  │  Primitive  │                 What it makes public                  │
  ├─────────────┼───────────────────────────────────────────────────────┤
  │ Split       │ Relation — the "between"                              │
  ├─────────────┼───────────────────────────────────────────────────────┤
  │ Trail       │ Becoming — how understanding formed                   │
  ├─────────────┼───────────────────────────────────────────────────────┤
  │ Event log   │ Causation — why the current state exists              │
  ├─────────────┼───────────────────────────────────────────────────────┤
  │ Artifact    │ Consequence — what understanding produced             │
  ├─────────────┼───────────────────────────────────────────────────────┤
  │ Local world │ Scope — what belongs together                         │
  ├─────────────┼───────────────────────────────────────────────────────┤
  │ Workflow    │ Traversal — the path between worlds                   │
  ├─────────────┼───────────────────────────────────────────────────────┤
  │ Synthesis   │ Plurality — how perspectives relate                   │
  ├─────────────┼───────────────────────────────────────────────────────┤
  │ Zoom        │ Continuity — that different scales are the same thing │
  └─────────────┴───────────────────────────────────────────────────────┘

  If you're building a feature and it doesn't externalize any of these, it's
  probably surface polish. If it externalizes one, it's useful. If it
  externalizes several at once, it's likely a high-leverage move.

  For example: click-to-navigate (clicking a trail card to open the file at that
   line in the editor pane) externalizes BOTH relation (trail node ↔ code) AND
  becoming (the temporal context of when that file was read during the agent's
  exploration). That's why it was identified as "THE killer feature" in
  where-we-are.md — not because it's technically impressive, but because it
  makes TWO dimensions of understanding public simultaneously.

  2. "Minimize private reconstruction" is the universal design criterion

  Codex said: "good design moves understanding from private reconstruction into 
  public structure." I think this is the single most actionable sentence for
  day-to-day product decisions.

  Every design choice can be evaluated against it:
  - Does this change REDUCE the amount of important structure the user must hold
   in their head? → Good.
  - Does this change INCREASE the amount of mental reconstruction required? →
  Bad, even if it looks clean or simple.

  This applies everywhere:
  - The refactor: wrong namespaces force every contributor to privately
  reconstruct what the system is. Right namespaces make it public.
  - A split: separating code and trail forces private reconstruction of their
  relation. Keeping them co-present makes it public.
  - Inline agent responses (the moonshot's ;;? pattern): keeping question and
  answer in the same spatial context eliminates private reconstruction of "what
  was I asking about?"
  - The sidebar showing file tree: makes project structure public rather than
  requiring the user to remember where things are.
  - Even design tokens: a consistent visual vocabulary means users don't have to
   privately decode what each color/size/spacing means.

  This criterion is also why "beautiful but empty" fails — it doesn't
  externalize anything meaningful, so the user still has to do all the
  understanding work privately.

  3. The preview pane as ontological question mark

  Codex's framing — the preview pane isn't waiting for content, it's waiting for
   the artifact taxonomy to stabilize — changes what "finishing" the preview
  pane means.

  The wrong approach: "what should we show in the right pane? Let's put
  something there."
  The right approach: "what durable artifact does each workflow produce? Once we
   know, the pane fills itself."

  For DG flow: the artifact might be the reasoning trail itself (viewed at a
  compressed zoom level — key decisions only, not every tool call). Or it might
  be the reviewed diff with inline trail annotations. Or it might be the
  synthesis across multiple agent runs on the same ticket.

  For JIT: the artifact is clearer — the compiled component, rendered live, with
   the token mapping visible.

  For future knowledge work: the artifact might be a discourse node — a claim
